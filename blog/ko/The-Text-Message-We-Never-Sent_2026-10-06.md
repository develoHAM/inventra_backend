# 우리가 끝내 보내지 않은 문자 한 통

> "이메일·SMS·푸시 알림"을 만들려고 시작했는데, 끝나고 보니 메시지를 잃지 않는 큐, 문자를 한 통도 보내지 않는 전화번호 인증, 그리고 `node_modules`를 열어 보고서야 알게 된 에러 코드의 교훈이 남았다.

*2026-10-06*

## 들어가며

[Inventra](https://github.com/develoHAM/inventra_backend)는 **NestJS 11 + Prisma 7 + PostgreSQL**로 만드는 멀티테넌트 재고 관리 SaaS입니다. 한국의 백화점 입점 매장 구조를 모델로 삼았습니다. 회사들이 매장 안에 "코너"를 운영하고, 오너·매니저·스태프가 재고를 함께 관리합니다.

이번 트랙은 지금까지 중 가장 컸습니다. **2주 동안 다섯 개의 슬라이스**를 진행했습니다.
1. 알림 파이프라인 (이벤트 → 큐 → 워커 → 이메일)
2. 여기에 연결한 비즈니스 이벤트 8종
3. 가입 시 전화번호 인증
4. 아이디 찾기와 비밀번호 재설정
5. Android·iOS·웹 푸시 알림

그 과정에서 계획의 SMS 부분은 전혀 예상하지 못한 모습으로 바뀌었습니다. 유닛 테스트는 233개에서 **514개**로, e2e는 87개에서 **140개**로 늘었습니다.

## 아키텍처 결정

### 1. 비즈니스 코드는 이벤트만 발행하고, 발송은 큐가 맡는다

**목표:** 어떤 서비스든 이메일·SMS·푸시를 전혀 몰라도 "주문이 생성됐다"고만 알리게 하고, 메일 서버가 죽어 있어도 알림을 잃지 않는 것.

**선택지:**
- 각 서비스 안에서 메일러를 직접 호출한다.
- 인메모리 이벤트를 발행하고, 리스너가 그 자리에서 메일을 보낸다.
- 이벤트를 발행하면 리스너가 `Notification` 행을 쓰고 **BullMQ** 잡을 넣고, 워커가 재시도와 함께 발송한다.

**결정:** 이벤트 + 큐.

**이유:**
- **그 자리에서 보내면 사용자의 요청이 SMTP를 기다리게 됩니다.** 메일 서버가 느리거나 죽어 있으면, 이메일과 아무 상관없는 주문 생성까지 느려지거나 실패합니다.
- **큐를 쓰면 백오프가 붙은 재시도를 얻고,** `Notification` 행이 모든 메시지의 영구 기록이 됩니다. PENDING → SENT / FAILED 상태와 `attempts`, `lastError`가 남습니다.

**결과:** `OrdersService`는 `eventEmitter.emit('order.created', { … })` 한 줄만 호출합니다. `NotificationsListener`가 이를 행으로 바꾸고 `WorkerHost`가 전달합니다. 나중에 푸시를 붙일 때도 비즈니스 서비스는 하나도 건드리지 않았습니다.

### 2. 커밋 후 발행: 트랜잭션 안에서 발행하지 말고 "보고"를 돌려준다

**목표:** 일어나지 않은 일을 알리지 않는 것. 예를 들어 나중에 롤백된 트랜잭션에서 나온 "재고가 목표 미달" 알림 같은 것.

**선택지:** `recordWithinTransaction` 안에서 바로 발행 / Prisma 미들웨어에서 발행 / 트랜잭션 코드가 바뀐 내용을 **반환**하고 `$transaction`이 끝난 뒤에 발행.

**결정:** 반환하고 모으기. `recordWithinTransaction`이 `{ ledgerEntry, stockChange }`를 반환하고, 호출자가 변경 내역을 모아 트랜잭션이 커밋된 **뒤에만** `emitStockAlerts(changes)`를 호출합니다.

**이유:** 이렇게 하면 롤백된 경우 발행하는 줄에 아예 도달하지 않습니다. 미묘한 오탐도 함께 잡을 수 있었습니다. 예약 이행은 RELEASE(+q) 다음 SALE(−q)인데, 쓰기를 하나씩 판단하면 실제로는 없었던 하락을 볼 수 있습니다. 그래서 알림은 **진열(placement)별로, 첫 "이전 값"과 마지막 "이후 값"을 비교해** 판단하고, 목표선을 **아래로 넘어서는 순간**에만 보냅니다.

**결과:** 재고가 목표선 아래로 내려가는 순간 정확히 한 번 알림이 가고, 이후 판매나 롤백된 쓰기에서는 가지 않습니다.

### 3. 멈춘 행을 구출하는 크론, `jobId` 덕분에 안전하다

**목표:** "행을 썼다"와 "잡을 넣었다" 사이에 Redis가 재시작되더라도 메시지는 결국 나가야 한다.

**결정:** 모든 잡에 `jobId = notification.id`를 쓰고, `@Cron(EVERY_5_MINUTES)` 리컨실러가 10분 넘게 `PENDING`인 행을 다시 큐에 넣습니다.

**이유:** BullMQ는 이미 존재하는 `jobId`로 들어온 `add()`를 무시합니다. 그래서 다시 넣는 작업이 **멱등**입니다. 잡이 아직 큐에 있으면 아무 일도 일어나지 않고, 사라졌다면 다시 만들어집니다.

**결과:** 약 30줄로, 중복 없는 "최소 한 번" 전달.

### 4. 방향 전환: 사용자가 *우리에게* 문자를 보내는 전화번호 인증

**목표:** 가입 시 인증된, 중복 없는 전화번호를 필수로 받는 것.

**선택지:**
- 전통적인 발신형 SMS 인증번호 (우리가 번호를 보내고 사용자가 입력).
- **OCTOMO 역방향 SMS(MO):** 우리는 코드를 화면에 *보여 주기만* 하고, 사용자가 자기 폰으로 `1666-3538`에 그 코드를 보내면, 우리는 OCTOMO API에 도착했는지 묻는다.

**결정:** OCTOMO. 발신형 설계를 이미 다 해 둔 뒤, 계획 중간에 내린 결정입니다.

**이유:**
- **발신자는 통신사가 증명합니다.** 코드가 담긴 문자가 010-1234-5678 *에서* 왔다면, 그 코드를 가진 사람이 그 폰을 쥐고 있다는 뜻입니다.
- **그래서 코드는 비밀이 아닙니다.** 화면에 그대로 보여 주므로 해시할 것도, 추측당할 것도 없습니다.
- **무료이고,** 발신 업체도, 발신번호 등록도, 발송 실패 처리도 필요 없습니다.

미리 써 둔 발신형 설계에는, 인증번호를 DB에는 남기지 않으면서도 워커에게는 전달하기 위한 "가려진(redacted)" 큐 잡이 필요했습니다. 이 모든 것이 사라졌습니다.

**결과:** `POST /auth/phone/start`는 `{ verificationId, code, receiverNumber }`를 돌려주고, `POST /auth/phone/confirm`은 `PhoneOwnershipVerifier`에 묻습니다. 운영에서는 OCTOMO, e2e에서는 가짜 구현입니다. 성공하면 **한 번만 쓸 수 있는 10분짜리 토큰**이 나오고, 가입이 자기 트랜잭션 안에서 그 토큰을 소모합니다.

### 5. 조건부 `updateMany`로 경쟁 상태에 강한 제한

**목표:**
- 인증 하나당 OCTOMO 확인은 최대 10번 (한 번마다 할당량을 씁니다)
- 인증 하나당 토큰은 정확히 하나
- 토큰은 정확히 한 번만 소모

**선택지:** 카운터를 읽고, JavaScript에서 판단한 다음 쓴다 / 조건을 **쓰기 안에** 넣는다.

**결정:** 조건부 쓰기. 예를 들어 `updateMany({ where: { id, checkAttempts: { lt: 10 } }, data: { checkAttempts: { increment: 1 } } })`를 실행하고 `count`를 확인합니다.

**이유:** 읽고-쓰는 방식의 카운터에 confirm 요청 25개를 동시에 보내는 시뮬레이션을 돌려 봤습니다. **25개가 전부 통과했고, 카운터는 2로 끝났습니다.** 모든 요청이 같은 낡은 값을 읽고 서로의 쓰기를 덮어썼기 때문입니다. 조건을 하나의 `UPDATE` 안에 넣으면 Postgres가 행을 잠그고, 11번째 요청은 바꿀 행을 찾지 못합니다.

**결과:** 세 규칙(확인 횟수 제한, 토큰 하나, 소모 한 번)을 명시적인 락 없이 한 가지 패턴으로 지킵니다.

### 6. 무언가를 알려 주기 전에 토큰부터 소모한다

**목표:** 낯선 사람이 조인 코드·전화번호·이메일을 공짜로 떠보지 못하게 하는 것.

**문제:** 멤버 가입이 전화번호 토큰을 확인하기 *전에* 조인 코드부터 조회했습니다. 404면 "그런 코드 없음", 그 밖의 응답이면 "이 코드는 존재함"을 뜻했으니, 추측하는 데 아무 비용이 들지 않았습니다.

**결정:** 모든 흐름이 인증 토큰을 **가장 먼저**, 트랜잭션 안에서 소모합니다. "일치 없음"이면 트랜잭션에서 **반환**하므로 커밋되고, 토큰은 소모된 채로 남습니다. 404/400은 그 뒤에야 던집니다.

**이유:** `$transaction` *안에서* 에러를 던지면 토큰 소모까지 롤백되어, 인증받은 폰 하나로 끝없이 떠볼 수 있게 됩니다. 던지지 않고 반환하는 것, 그것이 커밋과 롤백의 차이입니다.

**결과:** 떠보기 한 번에 실제 폰에서 보낸 실제 문자가 한 통 필요합니다(하루 10번 제한). 이메일 중복 경쟁 같은 진짜 실패는 여전히 롤백되므로, 정직한 사용자는 토큰을 잃지 않습니다.

### 7. 사람이 실제로 입력할 수 있는 조인 코드

**목표:** 오너가 자기 회사의 조인 코드를 *볼* 방법이 없었습니다(e2e는 DB에서 직접 읽고 있었습니다).

**결정:**
- `GET /companies/me/join-code`(오너 + 매니저), `POST …/rotate`(오너만)
- `INV-3FA91C07B2DE` 대신 8자리 숫자 코드
- 가입 시 공백·하이픈 제거

**이유:** 숫자는 소리 내어 읽기도, 손으로 받아 적기도 쉽습니다. 다만 10⁸개뿐이라 이제 충돌이 "절대 없음"은 아닙니다. 그래서 `generateUniqueJoinCode`가 이미 쓰인 코드를 뽑으면 최대 5번까지 다시 뽑습니다. `/me` 경로는 JWT에서 회사를 가져오므로, 다른 테넌트의 코드에 닿는 요청은 표현조차 할 수 없습니다.

### 8. 비밀번호 재설정은 두 가지 요소, 그리고 모든 기기 로그아웃

**결정:** `이메일 + 인증된 전화번호 + RESET_PASSWORD 토큰`. 하나의 트랜잭션 안에서 토큰 소모, 두 요소가 같은 계정을 가리키는지 확인, 해시 저장, 모든 refresh 토큰 폐기까지 처리합니다. 그 뒤에 계정 주인에게 "비밀번호가 변경되었습니다" 메일을 보냅니다.

**이유:** 폰만 훔쳐서는 부족합니다. 아이디 찾기는 `ow***@example.com`처럼 가린 이메일만 보여 주니까요. 세션 폐기는 이미 로그인해 있던 공격자를 쫓아냅니다. 알림 메일은 공격자가 필요로 하지 않았던 유일한 채널로 진짜 주인에게 닿습니다. 비밀번호 해시는 의도적으로 느리기 때문에 트랜잭션 *전에* 계산해서 DB 커넥션을 붙잡지 않게 했습니다.

### 9. 푸시: 기기마다 한 행, 죽은 토큰은 알아서 정리된다

**목표:** 모든 이벤트를 이메일 **그리고** 푸시로, Android·iOS·웹에.

**결정:**
- `DeviceToken` 테이블을 토큰 기준으로 upsert합니다. 다시 등록된 토큰은 새 사용자에게 *옮겨 가므로* 공용 폰 문제가 해결됩니다.
- 기기마다 `Notification` 행 하나.
- FCM 구현과 가짜 구현을 둔 `PushSender` 인터페이스.
- `EVENT_CHANNELS: Record<EventName, Channel[]>` 표로, 모든 이벤트의 채널을 컴파일 타임에 강제합니다.

**이유:** 기기별 행이라 각 기기가 독립적으로 재시도하거나 실패합니다. FCM이 토큰이 죽었다고 하면 워커가 `DeadDeviceTokenError`를 던지고, 그 기기를 지우고, 행을 FAILED로 표시한 뒤 **재시도하지 않습니다.** 사용자의 다른 기기는 영향을 받지 않습니다.

**결과:** 가짜 구현으로 만들고 끝까지 테스트했습니다. 실제 운영 전환은 환경 변수 두 개와 서비스 계정 키 하나면 됩니다.

## TIL (오늘 배운 것)

**"Nest에 이벤트가 이미 있는데 왜 BullMQ가 필요한가요?"**
이벤트는 메모리 안에서 쏘고 끝입니다. 프로세스가 죽으면 사라지고 재시도도 없습니다. 큐는 작업을 Redis에 저장하고 재시도합니다. 이벤트는 *누가 알리는지*를 떼어 내고, 큐는 *전달이 실제로 일어나는 것*을 보장합니다.

**"그 함정이 이해가 안 돼요."** (가려진 OTP 저장 이야기)
워커는 DB 행에 있는 텍스트를 그대로 보냅니다. 행에 `******`가 적혀 있어야 한다면, 진짜 코드는 잡 안처럼 다른 경로로 전달돼야 합니다. 그러면 *행만 보고* 잡을 다시 만드는 코드(리컨실러)는 사용자에게 `******`를 보내게 됩니다. 행, 잡, 폰을 값 하나하나 따라가 보고서야 이해했습니다. 결국 OCTOMO가 이 문제 자체를 없애 줬습니다.

**"`superRefine`과 `refine`은 정확히 뭐가 다른가요?"**
`refine`은 true/false를 반환하고 정해 둔 메시지 하나를 냅니다. `superRefine`은 파싱된 객체를 받아 `context.addIssue()`를 필요한 만큼 호출하고, 이슈마다 경로를 따로 지정합니다. 그리고 필드가 자기 규칙에서 이미 실패했다면 둘 다 실행되지 않으므로, 그 안에서는 모든 필드가 유효하다고 믿어도 됩니다.

**"`inject: [A, B, C]`는 순서대로 `useFactory`에 들어가나요?"**
네. 이름이나 타입이 아니라 오직 위치로 짝지어집니다. 배열 순서만 바꾸고 매개변수는 그대로 두면, `octomo`라는 이름의 매개변수에 조용히 가짜가 들어갑니다.

**"`AbortController`와 `AbortSignal`이 뭔가요?"**
Promise에는 취소 버튼이 없습니다. 컨트롤러는 리모컨(`abort()`)이고, 시그널은 `fetch`에 건네는 수신기입니다. `AbortSignal.timeout(5000)`은 스스로 버튼을 누르는 시그널입니다. 직접 돌린 데모에서 놀란 점이 있습니다. `fetch`는 **`signal.reason`**으로 reject되므로, `abort('어떤 문자열')`을 하면 `.name`이 없는 그냥 문자열로 reject됩니다.

**"HTTP 에러를 꼭 서비스 레이어에서 던져야 하나요?"**
아닙니다. 도메인 에러와 예외 필터를 쓰면 서비스를 HTTP에서 떼어 낼 수 있습니다. 하지만 서비스 14개가 전부 Nest HTTP 예외를 직접 던지고 있고, 호출하는 쪽도 HTTP뿐입니다. 바꿀 때는 큐 워커나 크론이 그런 서비스를 호출해야 할 때입니다.

**"`token`이 unique인데, 사용자 B가 같은 폰을 다시 등록하면 제약을 어기지 않나요?"**
어기지 않습니다. upsert는 기존 행을 찾아 *`userId`만 바꿉니다.* 그 토큰을 가진 행은 여전히 하나뿐입니다. 제약은 중복을 *삽입*할 때만 걸리고, `upsert`는 바로 그걸 피하려고 있는 것입니다.

**"FCM은 기기마다 영원히 고정된 토큰을 주나요?"**
아닙니다. 토큰은 앱 *설치* 하나에 속하고, 재설치, 데이터 삭제, 새 폰으로 복원, 가끔 일어나는 자동 갱신, 약 270일 미사용 시 바뀝니다. 그래서 앱은 실행할 때마다 다시 등록하고, 서버는 FCM이 죽었다고 알려 준 토큰을 지웁니다.

**"죽은 토큰 코드가 왜 `messaging/`으로 시작하나요? 문서에는 그런 게 없는데요."**
이번 트랙 최고의 질문이었습니다. SDK의 `MessagingErrorCode` enum 값은 `'registration-token-not-registered'`인데, 런타임의 `error.code`는 `'messaging/registration-token-not-registered'`입니다. 에러 생성자가 접두사를 붙이기 때문입니다. enum과 `===`로 비교했다면 **조용히 한 번도 일치하지 않았을 것이고,** 죽은 토큰은 영원히 재시도됐을 겁니다. SDK가 제공하는 `error.hasCode(code)`는 두 형태를 모두 받아 줍니다.

**"이거 Context7으로 확인한 건가요?"**
절반만요. API 모양은 Context7에서 확인했지만, 접두사가 붙은 코드는 기억에 의존했습니다. 실제로 결론을 낸 건 `node_modules/firebase-admin/lib/messaging/error.js`를 직접 읽고 실행해 본 것이었습니다. 남기고 싶은 교훈은 이것입니다. **문서는 어떤 버전을 설명할 뿐이고, `node_modules`가 *바로 지금 내 버전*이다.**

## 사용한 NestJS 개념과 라이브러리

| 개념 / 라이브러리 | 사용한 이유 |
|---|---|
| `@nestjs/event-emitter` (`@OnEvent`) | "무슨 일이 일어났다"와 "누구에게 알리나"를 분리 |
| `@nestjs/bullmq` (`WorkerHost`, `@InjectQueue`) | 재시도·백오프·`jobId` 멱등성을 갖춘 영속적인 전달 |
| `@nestjs/schedule` (`@Cron`) | 멈춘 PENDING 행을 구출하는 리컨실러 |
| nodemailer + Mailpit | SMTP 이메일, 개발·e2e에서는 Mailpit이 받아 API로 검증 |
| OCTOMO API (`fetch` + `AbortSignal.timeout`) | 무료 역방향 SMS 전화번호 인증 |
| firebase-admin (FCM) | 하나의 API로 Android·iOS·웹 푸시 |
| 인젝션 토큰 + `useFactory` | 환경별로 OCTOMO/가짜, FCM/가짜를 선택 |
| Zod `superRefine` | 여러 필드에 걸친 환경 변수 규칙 (예: `fcm`이면 키 경로 필수, 운영에서는 가짜 금지) |
| Prisma 조건부 `updateMany` / `upsert` | 경쟁 상태에 강한 횟수 제한, 1회용 토큰, 기기 재할당 |
| `Prisma.TransactionClient` | `consume()`이 호출자의 트랜잭션에 함께 참여 |
| `@Transform` + `@Matches` | 검증 전에 `010-1234-5678` → `01012345678`로 정규화 |
| `Record<Union, T>` | 컴파일러가 강제하는, 빠짐없는 이벤트→채널 표 |

# 누가 내 매니저를 옮겼을까?

> 승진·강등, 지점 간 이동. `UPDATE` 세 줄이면 끝날 것 같았습니다. 막상 해 보니 규칙표 하나, 잠금 순서 하나, 지울 수 없는 이력 하나, 그리고 "출입 명단"에 관한 뼈아픈 교훈 하나가 필요했습니다.

*2026-11-11*

## 들어가며

[Inventra](https://github.com/develoHAM/inventra_backend)는 **NestJS 11 + Prisma 7 + PostgreSQL**로 만드는 멀티테넌트 재고 관리 SaaS입니다. 한국의 백화점 입점 매장 구조를 모델로 삼았습니다. 회사들이 매장 안에서 "코너", 즉 지점을 운영하고, 오너·매니저·스태프가 재고를 함께 관리합니다.

이번 트랙은 **구성원 관리 개편 3부작 중 1부**, 역할과 지점입니다. 이제 오너와 플랫폼 관리자는 사람을 지점 사이로 옮기고, 승진·강등시키고, 신규 가입자를 승인하면서 역할과 지점을 한 번에 정해 줄 수 있습니다. 지점을 닫아도 그 안의 사람이 붕 뜨지 않습니다. 이 모든 변경은 지울 수 없고 읽을 수 있는 이력으로 남고, 당사자에게는 알림이 갑니다.

**6일 동안 8개 태스크**를 진행했고, 마지막에 전체 리뷰와 수정 한 차례를 거쳤습니다. 유닛 테스트는 880개에서 **1069개**로 늘었고, 전체 흐름을 실제 HTTP로 걷는 e2e 스위트가 새로 생겼습니다(16개 스위트, e2e **227개**).

## 아키텍처 결정

### 1. 매니저는 지점 하나: 외래 키의 방향이 규칙을 정한다

**목표:** 매니저나 스태프는 **지점 하나에 속하거나, 아무 데도 속하지 않는다.** 반대로 한 지점에는 매니저와 스태프가 여럿 있을 수도, 아무도 없을 수도 있다.

**선택지:**
- `company_stores.manager_user_id`(지점이 매니저를 가리킴)를 그대로 두고 규칙은 코드로 막는다.
- 사용자와 지점 사이에 조인 테이블을 두고 유니크 제약을 건다.
- **방향을 뒤집는다:** `users.company_store_id`, 즉 사람이 자기 지점을 가리킨다.

**결정:** 사람이 지점을 가리킨다. 스태프가 이미 쓰던 바로 그 컬럼입니다.

**이유:** 외래 키의 방향이 곧 카디널리티입니다.
- 지점 쪽 컬럼에는 매니저가 한 명만 들어가지만, 같은 매니저를 여러 지점이 가리킬 수 있습니다. "지점당 매니저 한 명, 매니저는 여러 지점"이 되니 원하는 것과 정반대입니다.
- 사용자 쪽 컬럼에는 지점이 하나만 들어가고, 그 지점은 몇 명이든 가리킬 수 있습니다. "한 사람당 지점 하나"를 유니크 인덱스도, 코드도 없이 데이터베이스가 공짜로 지켜 줍니다.

**결과:** "누가 어디 있는가"의 기준이 하나로 정리됐습니다. 지점의 매니저 연결, 배정용 엔드포인트 세 개, `corners.assign` 권한이 모두 사라지고 `PUT /users/:id/branch` 하나로 대체됐습니다.

마이그레이션에서도 배운 게 있습니다. 계획은 정석대로 **확장 → 이전 → 축소**였습니다. `--create-only`로 마이그레이션을 만들고, 각 지점의 매니저를 `users.company_store_id`로 옮기는 데이터 단계를 손으로 넣은 뒤 적용하는 순서였죠. 그런데 데이터 단계를 넣기 **전에** 적용돼 버렸습니다. Prisma는 적용된 마이그레이션마다 체크섬을 기록하므로, 나중에 그 파일을 고치면 이후 모든 `migrate`가 변조된 것으로 판단합니다. 그래서 **데이터만 다루는 후속 마이그레이션**을 따로 추가했습니다. 그 전에 잃을 매니저 연결이 실제로 있는지 읽기 전용으로 먼저 확인했고, 하나도 없었습니다. 그때 정한 원칙: 어딘가에서 이미 실행됐을 수 있는 마이그레이션은 절대 고치지 않고, 새로 하나를 더한다.

### 2. 변경 전후를 통째로 담는, 추가만 되는 이력

**목표:** "이 사람을 언제 누가 B 지점으로 옮겼지?"라는 질문에 사람별·지점별·회사별로 영원히 답할 수 있어야 한다.

**선택지:**
- `updatedAt` 컬럼. 바뀌었다는 사실만 알려 주고 무엇이 바뀌었는지는 모릅니다.
- 바뀐 필드만 기록하는 로그.
- 데이터베이스 트리거.
- **변경 하나당 한 행, 전후 값을 모두 담아서**, 변경을 일으키는 코드가 직접 쓴다.

**결정:** `membership_changes` 테이블입니다. 이전/이후 역할, 이전/이후 지점, `reason`(`APPROVED | MOVED | ROLE_CHANGED | BRANCH_DELETED`), `changed_by_user_id`(null이면 시스템)를 담고, 변경 자체와 **같은 트랜잭션** 안에서 씁니다.

**이유:**
- **전후를 통째로 담으면 모든 조회가 단순해집니다.** A 지점 매니저가 A 지점 스태프를 승진시키면 `from = to = A`인 행이 남습니다. 그래서 "A 지점 이력"은 "A가 from이거나 to인 행"이면 끝입니다. 바뀐 필드만 남겼다면 이 승진 기록에는 A가 아예 등장하지 않았을 겁니다.
- **같은 트랜잭션**이므로 변경과 이력은 함께 커밋되거나 함께 롤백됩니다. 이동은 있는데 기록이 없거나, 기록은 있는데 이동이 없는 일은 생기지 않습니다.
- 행은 수정도 삭제도 하지 않으므로, 이 저장 방식은 첫 마이그레이션부터 맞아야 했습니다.

**결과:** 읽기 엔드포인트 세 개(사람의 타임라인, 지점의 이력, 회사 전체 피드)가 테이블 하나에 대한 `where` 세 개로 끝났습니다.

### 3. 역할 규칙표를 순수 함수로

**목표:** 승진·강등 규칙에는 경우의 수가 열 개 넘게 있습니다(누가 누구를, 무엇으로 바꿀 수 있는지, 그때 지점은 어떻게 되는지). 이걸 데이터베이스 없이 전부 테스트하고 싶었습니다.

**선택지:** 서비스 안, 트랜잭션 옆에 `if`를 줄줄이 쓴다. 아니면 결정만 돌려주는 **순수 함수**를 만든다.

**결정:** 데이터베이스도 부수 효과도 없는 함수 `decideRoleChange`입니다.

```ts
type RoleChangeDecision =
  | 'noop'
  | { branch: 'keep' | 'clear' | 'set'; checkOwnerCount: boolean };
```

- `keep`: 스태프 ↔ 매니저는 지점을 그대로 유지합니다.
- `clear`: 오너로 승진하면 지점을 떠납니다(오너는 지점이 없습니다).
- `set`: 관리자가 오너를 강등할 때 새 지점(또는 `null`)을 고릅니다.
- `checkOwnerCount`: 오너 강등만, 오너가 한 명 이상 남는지 증명해야 합니다.

**이유:** 서비스는 결정을 *실행*하기만 합니다. 규칙표는 스펙의 표를 한 줄씩 그대로 테스트합니다. 자기 자신을 강등하는 경우, 그리고 "지점 없는 매니저는 지점 없는 스태프를 승진시킬 수 없다"(`null === null`을 같은 지점으로 치면 안 됨) 같은 경우까지 포함해서요.

**결과:** 이번 트랙에서 가장 까다로운 로직이 가장 단순한 테스트를 갖게 됐고, 서비스 코드는 레시피처럼 읽힙니다.

### 4. `SELECT … FOR UPDATE` 없이 동시성 다루기

**목표:** 관리자 두 명이 마지막 오너 두 명을 동시에 강등해도 오너는 정확히 한 명 남아야 한다. 지점으로의 이동과 그 지점의 삭제가 동시에 일어나도, 삭제된 지점에 사람이 남으면 안 된다.

**선택지:** 읽고, 확인하고, 쓴다(그리고 운에 맡긴다). 데이터베이스 에러를 잡는다. 아니면 **충돌하는 요청을 데이터베이스가 줄 세우게 한다.**

**결정:** 네 가지 습관을 함께 씁니다.
- **쓰기로 잠그기.** Prisma에는 `FOR UPDATE`가 없습니다. 하지만 모든 `UPDATE`는 커밋할 때까지 그 행의 잠금을 쥐고 있습니다. 그래서 "이 지점을 잠근다"는 `updatedAt`만 갱신하는 `updateMany`이고, 그 count가 지점이 아직 살아 있는지 알려 줍니다.
  ```ts
  const locked = await transaction.companyStore.updateMany({
    where: { id: cornerId, companyId: companyId, deletedAt: null },
    data: { updatedAt: new Date() },
  });
  return locked.count === 1;
  ```
- **조건부 쓰기.** 구성원 행을 갱신할 때 `where`에 *이전* 값을 넣습니다. 방금 누가 바꿨다면 일치하는 행이 없어 `count`가 0이 되고, 응답은 409 "새로고침하세요"입니다.
- **오너 수는 회사 행으로.** 두 강등 요청이 각자 "오너 2명"을 세고 각자 한 명씩 강등하는 상황은 *쓰기 왜곡(write skew)*입니다. 두 쓰기는 서로 충돌하지 않는데, 합쳐지면 규칙이 깨집니다. 이제 둘 다 회사 행을 먼저 쓰므로, 두 번째 요청은 기다렸다가 첫 번째가 남긴 결과를 셉니다.
- **잠금 순서는 어디서나 하나:** 회사 → 지점 → 구성원. 두 요청이 반대 순서로 잠그면 교착 상태에 빠질 수 있습니다. 순서가 하나뿐이면 그럴 수 없습니다.

그리고 이벤트(알림)는 트랜잭션이 커밋된 **뒤에** 발행합니다. 롤백된 변경을 알림으로 받는 사람이 없도록요.

**결과:** 경합은 Postgres가 판정하고, 코드는 에러 메시지를 파싱하는 대신 count라는 단순한 답만 읽습니다.

### 5. 지점 닫기: 사진이 아니라 영수증

**목표:** 지점을 삭제하면 그 안의 모두를 풀어 주고, 한 사람당 `BRANCH_DELETED` 이력 한 행과 알림 하나를 남긴다.

**선택지:** 지점의 사람들을 `findMany`로 읽은 뒤 `updateMany`로 갱신한다(쓰기 전에 찍은 *사진*). 아니면 **`updateManyAndReturn`**을 쓴다(쓰기가 실제로 바꾼 것의 *영수증*).

**결정:** 영수증입니다.

```ts
const releasedMembers = await transaction.user.updateManyAndReturn({
  where: { companyStoreId: id, deletedAt: null },
  data: { companyStoreId: null },
  select: { id: true, roleId: true },
});
```

**이유:** 사진 방식에서는 읽기와 갱신 사이에 다른 지점으로 옮겨 간 사람도 "지점이 삭제됐습니다" 기록과 알림을 받습니다. 영수증 방식에는 그 틈이 없습니다. 같은 문장 안에서, 갱신이 실제로 건드린 행만 정확히 돌려줍니다.

**결과:** 이력과 알림이 언제나 실제로 일어난 일과 일치합니다.

### 6. `undefined`, `null`, 값은 서로 다른 세 가지 대답이다

**목표:** 승인할 때는 신규 가입자를 어디에 둘지 반드시 말해야 한다("아직 지점 없음" 포함). 역할 변경에서는 관리자가 오너를 강등하는 경우가 아니면 지점을 받지 않아야 한다.

**선택지:** "안 보냄"과 `null`을 같은 것으로 본다. 아니면 세 상태를 모두 구분한다.

**결정:** 세 상태를 구분합니다.
- 승인: `cornerId`는 **필수지만 null 허용**입니다(`@ValidateIf((dto) => dto.cornerId !== null) @IsUUID()`). 아무것도 안 보내면 400, `null`은 "아직 지점 없음"입니다.
- 역할 변경: `cornerId`는 **선택**이고, 서비스는 `dto.cornerId !== undefined`로 *보냈는지 여부* 자체를 확인합니다.

**이유:** "말하지 않았다"와 "없다고 말했다"는 다른 의도입니다. 둘을 합치면 모든 역할 변경에 지점을 강요하거나, 승인에서 지점을 조용히 빠뜨리게 됩니다.

**결과:** 각 엔드포인트가 자기에게 필요한 질문만 정확히 묻고, 검증 메시지도 그렇게 말합니다.

### 7. 누가 누구를 보는가: 읽기는 회사 전체, 승인 대기자는 진짜 승인자에게만

**목표:** 동료끼리는 서로 연락할 수 있어야 한다. 하지만 아직 승인을 기다리는 사람은 동료가 아니다.

**선택지:** 지점 단위 구성원 목록. 모두가 모두를 본다. 아니면 **회사 전체 목록에 예외 하나**.

**결정:**
- `GET /users`는 회사 전체를 **전화번호와 연락용 이메일까지** 보여 줍니다. `?cornerId=`(URL로는 `null`을 보낼 수 없어서 `none`이 "지점 없음"), `?role=`, `?status=`로 걸러 볼 수 있습니다.
- 승인 대기자는 그들을 **실제로** 승인할 수 있는 사람에게만 보입니다. `users.approve` 권한이 있고, **동시에** `approve`가 받아 주는 역할(관리자, 오너, 지점이 *있는* 매니저)이어야 합니다.

**이유:** "실제로 승인할 수 있는"이라는 표현은 마지막 리뷰에서 나왔습니다(결정 9). 그 밖의 사람에게는 승인 대기자가 걸러지고, `?status=PENDING_APPROVAL`로 직접 물어도 403 대신 빈 목록이 돌아갑니다. 403은 그런 사람이 있다는 사실을 확인해 주기 때문입니다.

**결과:** 회사 전체가 하나의 목록을 쓰면서도, 승인 대기열은 그걸 처리할 수 있는 사람에게만 보입니다.

### 8. 넘겨 볼 수 있는 이력: 쪽 번호가 아니라 책갈피

**목표:** 긴 이력을 최신순으로, 페이지 단위로 읽는다. 위쪽에 새 항목이 계속 쌓여도 중복이나 누락이 없어야 한다.

**선택지:** 오프셋 페이징(`skip: 50`). 아니면 **커서 페이징**.

**결정:** 커서입니다. Prisma의 `cursor`, `take`, `skip`에 제가 만든 장치 두 개를 더했습니다.

```ts
const rows = await this.prisma.membershipChange.findMany({
  where: where,
  orderBy: [{ createdAt: 'desc' }, { id: 'desc' }],
  take: limit + 1,
  ...(query.cursor ? { cursor: { id: query.cursor }, skip: 1 } : {}),
  select: MEMBERSHIP_CHANGE_SELECT,
});
const hasMore = rows.length > limit;
const items = rows.slice(0, limit).map((row) => toMembershipChangeView(row));
return { items: items, nextCursor: hasMore ? items[items.length - 1].id : null };
```

**이유:**
- **오프셋은 맨 위부터 위치를 셉니다.** 새 항목이 맨 위에 들어오면 모든 위치가 밀려서 같은 항목이 또 나옵니다. 커서는 특정 항목을 가리키므로 새로 들어온 항목에 밀리지 않습니다.
- **Prisma의 커서는 그 행을 포함합니다.** `cursor: { id }`는 책갈피 행, 즉 앱이 이미 보여 준 마지막 행*부터* 시작합니다. 그래서 `skip: 1`로 그 행을 건너뜁니다.
- **`limit + 1`은 살짝 엿보기입니다.** 보여 줄 것보다 하나 더 가져와서, 그게 있으면 다음 페이지가 있는 겁니다. `COUNT` 쿼리가 필요 없습니다.
- **`id`가 동점을 가릅니다.** 한 문장으로 쓴 행들은 타임스탬프가 마이크로초까지 같습니다(직접 확인했습니다. 두 명이 있던 지점을 닫았더니 `created_at`이 완전히 같은 행 두 개가 생겼습니다). 시간만으로 정렬하면 동점 행의 순서는 데이터베이스 마음이고, 그 사이에 페이지 경계가 걸리면 한 행은 두 번 나오고 다른 한 행은 영영 안 나올 수 있습니다.

그 앞에는 접근 규칙이 있습니다. 다른 회사의 사람·지점·피드는 **404**입니다(존재 여부조차 확인해 주지 않습니다). 그다음에야 역할 확인으로 **403**이 나옵니다. 항목에는 id와 이름만 담기고, 전화번호나 이메일은 절대 담기지 않습니다.

**결과:** e2e 테스트가 회사 피드 전체를 한 항목씩 넘겨 보며, 동점 행까지 포함해 중복도 누락도 없는지 확인합니다.

### 9. 마지막 리뷰, 그리고 출입 명단

**목표:** 태스크 하나하나가 아니라 브랜치 전체를 다른 눈으로 한 번 더 본다.

**선택지:** 태스크별 테스트를 믿는다. 내가 직접 리뷰한다. 아니면 계획서의 "리뷰 중점" 목록과 그동안 기록해 둔 모든 판단을 넘겨서 **새 리뷰어를 투입한다.**

**결정:** 새 리뷰어를 투입했고, 이어서 **수정은 한 번만** 했습니다. 각 수정은 먼저 실패하는 테스트로 증명했습니다.

**발견한 것:**
- **진짜 구멍 하나.** 회사 가입은 오너를 OWNER 역할을 *가진 채로* `PENDING_APPROVAL` 상태로 저장합니다. 가입 코드로 들어오는 구성원은 역할 없이 대기합니다. 그런데 `approve`는 "대기 중인가"만 확인했습니다. 그래서 관리자가 회사의 대기 중인 오너를 스태프로 승인해 버리면 그 회사에는 오너가 한 명도 남지 않았습니다. 수정: 이미 역할이 있는 대기자는 거부하고(400), 조건부 쓰기에도 `roleId: null`을 추가했습니다.
- **다른 규칙은 전부 출입 명단(허용 목록)인데, 여기만 블랙리스트였다.** 예전 검사는 *제한할* 역할만 이름으로 적었습니다.
  ```ts
  if (caller.roleCode === 'MANAGER') { /* 스태프로만, 자기 지점으로만 */ }
  // 나머지 모두: 제한 없음
  ```
  여기에 이름이 없는 역할은 STAFF를 포함해 모두 오너급 권한을 가졌습니다. 그래도 안전해 보였던 건 권한 가드가 스태프를 아예 들여보내지 않았기 때문입니다. 그런데 Inventra는 **사용자별 권한 예외**도 지원합니다. 역할 권한 위에 `GRANT`나 `DENY` 행을 얹는 방식인데, 가드는 그 권한이 어디서 왔는지 구분하지 못합니다. 그래서 `users.approve`를 개인 `GRANT`로 받은 스태프는 가드를 통과해서, 아무 지점에나 누군가를 매니저로 승인할 수 있었습니다. 이제 검사는 **허용되는** 역할을 적고, 나머지는 전부 403입니다.
  ```ts
  const isAdminOrOwner = caller.roleCode === 'ADMIN' || caller.roleCode === 'OWNER';
  if (!isAdminOrOwner) {
    if (caller.roleCode !== 'MANAGER') throw new ForbiddenException('Only owners and managers can approve members');
    /* 스태프로만, 자기 지점으로만 */
  }
  ```
- **이름을 지워 버릴 수 있던 이력의 외래 키.** Prisma는 *선택적* 관계의 기본값을 `ON DELETE SET NULL`로 둡니다. 행위자가 하드 삭제되면 `changedBy: null`이 되는데, 우리 API는 이걸 "시스템이 한 일"로 읽습니다. 이제 일곱 개 모두 `ON DELETE RESTRICT`입니다. 이력이 가리키는 것은 데이터베이스가 삭제를 거부하므로, "삭제된 사람의 이름도 기록에 남는다"는 원칙이 가장 낮은 층에서 지켜집니다.
- **다른 피드의 책갈피**를 보내면 조용히 엉뚱한 페이지가 나왔습니다. 이제는 400입니다.
- **실패할 수 없던 동시성 테스트.** "두 강등을 동시에"는 두 요청이 우연히 겹치지 않으면 잠금이 있든 없든 통과합니다. 새 테스트는 회사 행 잠금을 *테스트가 직접* 쥐고 강등 요청을 보낸 뒤, 0.5초가 지나도 아직 기다리고 있는지 확인하고, 잠금을 풀어 409를 기대합니다. 코드에서 잠금이 빠지면 이 테스트는 실패합니다.

**결과:** 발견된 것은 모두 고쳤고, 리뷰어가 "판단 보류"로 남긴 항목들은 말없이 넘긴 가정이 아니라 글로 남긴 결정이 됐습니다.

## TIL (오늘 배운 것)

**"`updateMany`가 어떻게 지점을 잠그나요? Prisma의 표준 비관적 잠금, `FOR UPDATE`인가요?"**
Prisma에는 `FOR UPDATE`가 아예 없습니다. Postgres는 *모든* `UPDATE`에 행 잠금을 걸고 트랜잭션이 끝날 때까지 쥐고 있습니다. 그러니 행을 쓰는 것 자체가(`updatedAt`만 바꾸더라도) 잠금입니다. 같은 행을 쓰려는 두 번째 트랜잭션은 기다렸다가, 커밋된 행을 기준으로 자기 `where`를 다시 확인합니다.

**"`$transaction`은 무엇으로 커밋과 롤백이 갈리나요? 안에서 에러가 나면요?"**
콜백이 정상적으로 끝나면 커밋입니다. `null`을 돌려줘도 마찬가지입니다. 콜백이 throw하면 전부 롤백되고, *같은* 에러가 호출한 쪽으로 다시 던져집니다. 함정이 두 개 있습니다. 콜백 안에서 `this.prisma`로 보낸 쿼리는 트랜잭션에 포함되지 않습니다. 그리고 이메일 같은 부수 효과는 롤백되지 않습니다. 그래서 이벤트는 커밋 뒤에 발행합니다.

**"A에서 나가는 건 A를 잠그지 않고 B만 잠근다면, B가 잠긴 동안에는 누구의 지점도 B가 될 수 없다는 뜻인가요?"**
조금 다릅니다. 잠기는 건 B의 *행*이지 누군가의 `company_store_id`가 아닙니다. B로의 이동도 B의 행을 쓰고, B의 삭제도 B의 행을 쓰므로 둘은 차례를 지킵니다. 삭제가 먼저면, 이동은 `deletedAt`이 채워진 것을 보고 404를 답합니다. 이동이 먼저면, 삭제가 그 사람까지 함께 풀어 줍니다. 어느 쪽이든 삭제된 지점에 남는 사람은 없습니다.

**"추가 규칙은 쿼리가 아니면 어디서 확인하나요?"**
쿼리 뒤에, 돌아온 행을 보고 확인합니다. 테넌트 필터는 `where`에 스프레드로 들어갑니다. 그 뒤에 조건을 더 스프레드하면 이름이 같은 키가 `companyId`를 조용히 덮어쓸 수 있습니다. 그래서 `findTarget`은 테넌트 필터만으로 조회하고, 행을 코드에서 걸러 냅니다(회사가 없거나 구성원 역할이 아니면 404).

**"`satisfies Prisma.UserSelect`는 뭔가요?"**
`select` 객체가 올바른 select인지 검사합니다(오타는 컴파일 에러가 납니다). 그러면서도 타입을 넓히지 **않습니다.** 그래서 `Prisma.UserGetPayload<{ select: typeof MEMBER_SELECT }>`가 여기서 정확한 행 타입을 그대로 끌어낼 수 있습니다.

**"애초에 `cornerId`가 `undefined`일 수 있게 둔 이유는요?"**
"안 보냄"과 "`null`로 보냄"은 뜻이 다르기 때문입니다. 역할 변경에서 지점을 보낼 수 있는 건 오너를 강등하는 관리자뿐입니다. 그래서 서비스는 값이 null인지가 아니라, 애초에 보냈는지를 알아야 합니다.

**"커서는 Prisma 기능인가요? 그리고 커서는 다음 페이지의 첫 행 아닌가요?"**
`cursor`, `take`, `skip`은 Prisma `findMany`의 옵션이고, `limit + 1`과 `nextCursor`는 제가 만든 것입니다. 제가 내주는 커서는 **앱이 이미 보여 준 마지막 행**입니다. Prisma의 커서는 그 행을 *포함*하므로 `skip: 1`로 빼 줍니다. 다음 페이지의 첫 행을 내주고 건너뛰지 않는 방식도 동작합니다. 저는 문서에 나온 패턴, 즉 앱이 이미 가진 행을 책갈피로 쓰는 쪽을 택했습니다.

**"왜 `id`로도 정렬하나요?"**
한 문장으로 쓴 행들은 `created_at`이 같습니다. 시간만으로 정렬하면 동점 행의 순서는 데이터베이스 마음대로입니다. 그 사이에 페이지 경계가 걸리면 한 행은 두 번 나오고 다른 행은 끝내 안 나올 수 있습니다.

**"'블랙리스트가 아니라 출입 명단'이라는 게 무슨 뜻인가요?"**
허용 목록(출입 명단)은 들어올 수 있는 사람을 적으므로, 예상 못 한 경우는 거부됩니다(닫힌 쪽으로 실패). 거부 목록(블랙리스트)은 제한할 사람을 적으므로, 예상 못 한 경우는 그냥 들어옵니다(열린 쪽으로 실패). 미리 생각해 둔 경우에는 둘의 답이 같습니다. 달라지는 건 생각 못 한 경우뿐인데, 버그는 바로 거기에 삽니다.

**"GRANT가 뭔가요? 역할 권한 말고 사용자별 예외도 있다고요?"**
네. `user_permissions`에 사용자별 `GRANT`나 `DENY` 행이 있고, 역할 권한 위에 합쳐집니다. 가드는 합쳐진 결과만 보므로, GRANT는 역할을 바꾸지 않고도 할 수 있는 일을 바꿉니다. 그래서 서비스의 역할 규칙은 예상하지 못한 역할을 거부해야 합니다.

**"지점 없는 매니저가 어떻게 생기나요?"**
다섯 가지 경로가 있습니다. "아직 지점 없음"으로 매니저 승인을 받았을 때, 지점에서 빠지도록 이동됐을 때, 지점이 삭제됐을 때, 지점 없는 스태프가 매니저로 승진했을 때, 관리자가 오너를 지점 없이 강등했을 때입니다. 이들은 아무도 승인할 수 없으니, 승인 대기열도 보지 못합니다.

## NestJS 개념과 라이브러리

| 개념 / 라이브러리 | 쓴 이유 |
|---|---|
| Prisma 대화형 `$transaction` + `Prisma.TransactionClient` | 변경과 이력을 함께 커밋하거나 함께 롤백 |
| Prisma `updateMany` + `count` | 조건부 쓰기(경합에서 지면 409)와 쓰기로 잠그기 |
| Prisma `updateManyAndReturn` | 지점의 사람들을 풀어 주면서 정확히 누구인지 한 문장으로 받기 |
| `cursor` / `take` / `skip`과 복합 `orderBy`를 쓴 Prisma `findMany` | 동점 처리까지 된 커서 페이징 이력 |
| Prisma 이름 붙은 관계(`@relation("MembershipChangeActor")`) | 한 테이블에서 `users`·`roles`·`company_stores`로 가는 관계 여러 개 |
| Prisma `onDelete: Restrict` | 이력이 가리키는 이름이 사라지지 않게 |
| `prisma migrate dev --create-only` + 데이터 전용 마이그레이션 | 손으로 쓴 데이터 단계, 적용된 마이그레이션을 고치지 않는 복구 |
| `satisfies Prisma.UserSelect` + `Prisma.UserGetPayload` | 검사받는 `select`와 그 select가 돌려주는 정확한 행 타입 |
| class-validator `@ValidateIf`, `@IsOptional`, `@IsIn`, `@IsEnum`, `@IsUUID` | 필수지만 null 허용 vs 선택 필드, 쿼리 필터 |
| class-transformer `@Type(() => Number)` + `ValidationPipe({ transform: true })` | 텍스트로 들어온 `?limit=20`을 숫자로 바꿔 내보내기 |
| `@Query()` DTO와 `ParseUUIDPipe` | 검증된 쿼리 문자열, 형식이 틀린 id는 DB 에러가 아니라 400 |
| `@nestjs/event-emitter` 리스너 | 알림은 커밋 뒤에만 발행 |
| `Record<MemberRoleCode, string>` | 역할이 하나라도 빠지면 컴파일되지 않는 한국어 역할 이름 |
| Postgres `pg_constraint`(e2e에서) | 이력의 외래 키가 전부 RESTRICT인지 확인 |

## 마무리

이번 트랙에서 만든 것:
- **매니저·스태프는 지점 하나**, 지점 간 이동, 그리고 그 안의 사람을 풀어 주는 지점 삭제
- 테스트된 순수 규칙표로 움직이는 **승진과 강등**. "회사에는 항상 오너가 남는다"는 규칙을 동시성 아래에서도 지킴
- 역할과 지점을 한 번에 정해 주는 **승인**
- 사람·지점·회사별로 읽을 수 있고 커서로 넘겨 보는, **추가만 되는 구성원 이력**
- 모든 이동과 역할 변경에 대한 한국어 **알림**
- 동료끼리는 연락할 수 있고, 승인 대기열은 승인자에게만 보이는 구성원 목록
- 이번 트랙 이전부터 있던 구멍까지 포함해, 발견된 것을 전부 고친 마지막 리뷰

남기고 싶은 교훈: 접근 검사는 **출입 명단**으로 쓰자. 제한할 대상만 적은 규칙은 그 앞의 모든 층이 안전할 때만 안전합니다. 그리고 다음 기능(이번에는 사용자별 권한 예외)이 언젠가 그 층 하나를 열게 됩니다.

다음 편: **2부, 로그인 하나에 회사별 프로필.** 지금은 전화번호 하나가 정확히 한 회사에 묶여 있습니다. 다음에는 한 번 로그인한 사람이 Slack 워크스페이스처럼 회사들 사이를 오가고, 계정과 회사 프로필이 서로 다른 것이 됩니다.

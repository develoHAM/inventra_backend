# 폰 하나, 명찰 둘

> 한 사람이 두 회사에서 일할 수 있게 하는 일. 테이블 하나 추가하면 끝날 줄 알았습니다. 막상 해 보니 마이그레이션 세 번, 토큰 재설계, 초대 코드 무작위 대입을 막는 브레이크, 쓰기로 거는 잠금, 그리고 모든 테스트가 기대고 있던 엔드포인트 두 개를 없애는 일까지 필요했습니다.

*2026-11-19*

## 들어가며

[Inventra](https://github.com/develoHAM/inventra_backend)는 **NestJS 11 + Prisma 7 + PostgreSQL**로 만드는 멀티테넌트 재고 관리 SaaS입니다. 한국의 백화점 입점 매장 구조를 모델로 삼았습니다. 회사들이 백화점 안에서 지점("코너")을 운영하고, 오너·매니저·스태프가 재고를 함께 관리합니다.

이번 트랙은 **구성원 관리 개편 3부작 중 2부, "로그인 하나로 여러 회사"** 입니다. 지금까지는 전화번호 하나가 정확히 회사 하나에 묶여 있었습니다. 주중엔 A 브랜드, 주말엔 B 브랜드에서 일하는 파트타이머라면 계정 둘, 비밀번호 둘, 앱 둘이 필요했죠. 이제는 한 번 가입하고, 앱 안에서 회사에 합류하거나 회사를 만들고, Slack 워크스페이스처럼 회사를 오가며 일할 수 있습니다. 회사마다 이름·사진·연락용 이메일을 따로 두고, 폰 하나로 모든 회사의 알림을 받되 어느 회사의 알림인지 표시됩니다.

**8일** 동안 태스크 7개에, 중간에 이름 바꾸기 태스크 하나, 마지막에 제가 요청한 후속 작업 하나를 진행했습니다. 유닛 테스트는 1069개에서 **1238개**로, e2e는 227개에서 17개 스위트 **271개**로 늘었습니다. 기존 16개 스위트를 전부 다시 썼는데도 마지막 실행은 한 번에 통과했습니다.

## 아키텍처 결정

### 1. "나는 누구인가"와 "회사에서의 나"를 나누다

**목표:** 한 사람에게 로그인은 하나(전화번호, 비밀번호, 카카오·애플 로그인, 세션, 기기)이고, **회사마다 프로필은 따로**(이름, 사진, 연락용 이메일, 역할, 지점, 상태) 있게 하기.

**선택지:**
- `users` 테이블을 두고 사용자와 회사 사이에 `memberships` 조인 테이블을 추가한다.
- 새 테이블 두 개를 만들고 전부 옮긴다.
- **로그인용 `accounts` 테이블을 새로 만들고, `users`는 회사별 프로필로 그대로 둔다.**

**결정:** 세 번째. 로그인만 `accounts`로 빼내고, 기존 `users` 행은 그 자리에 둔 채 프로필이 되게 했습니다.

**이유:** 회사 쪽 관계(발주, 재고 실사, 재고 이동, 이력, 알림)는 전부 *로그인*이 아니라 *회사 안의 사람*을 가리킵니다. 그 행을 그대로 두면 외래 키를 하나도 옮길 필요가 없습니다. 게다가 마이그레이션되는 계정이 **기존 사용자의 id를 그대로 재사용**하도록(`accounts.id = users.id`) 했더니, 데이터 단계가 조회도 매핑 테이블도 없는 단순 복사가 됐습니다.

```
expand   → accounts 생성, nullable account_id 컬럼 추가
copy     → INSERT INTO accounts SELECT id, phone … FROM users; 로그인·세션·기기를 새로 연결
contract → NOT NULL로 바꾸고, 옛 컬럼과 외래 키 삭제
```

**결과:** Task 1은 동작을 하나도 바꾸지 않았고, 그게 목표였습니다. 기존 e2e 227개가 그대로 통과했고, 기존 사용자는 비밀번호·카카오·애플 연결·기기를 모두 그대로 유지했습니다.

### 2. 이름도 문서다. 그래서 이름만 바꾸는 마이그레이션을 따로 (그리고 한 번 마음을 바꿨다)

**목표:** 로그인을 떼어 내고 나니 `users` 테이블은 사실상 *회사 프로필*이었습니다. 그런데 코드에서는 여전히 `User`, `AuthUser`, `request.user`, `users.*` 권한이라고 부르고 있었습니다.

**선택지:** 옛 이름을 그냥 쓴다 / 코드에서만 바꾼다(`@@map`으로 옛 테이블 유지) / **DB까지 전부 바꾼다.**

**결정:** 전부 바꿨습니다. 마이그레이션은 `RENAME` 54개(테이블, enum, 컬럼, 기본 키, 외래 키, 인덱스)와 권한 코드를 고치는 `UPDATE` 하나뿐이고, 행은 하나도 옮기지 않습니다.

**이유:** 실제로는 "한 회사 안의 사람"인데 이름이 `User`인 모델은 앞으로 코드를 읽을 모든 사람, 저 자신까지 헷갈리게 합니다. `RENAME`은 데이터도 id도 모든 행도 그대로 둡니다.

고백할 게 하나 있습니다. 처음에는 로그인을 **User**, 회사 쪽을 **Profile**로 정했습니다. 그런데 중간에, "user"야말로 사람마다 다르게 받아들이는 단어라는 걸 깨닫고 로그인을 **Account**로 바꿨습니다. 첫 시도는 git stash에 넣어 두었는데, 그 마이그레이션은 한 번도 적용된 적이 없어서 미련 없이 버릴 수 있었습니다. 그 뒤로 프로젝트 가이드에 용어 규칙이 생겼습니다. *"User"라는 이름의 모델은 두지 않는다.*

**결과:** `Account`는 로그인, `Profile`은 한 회사 안의 사람이고, "누가 기록했는가"는 전부 프로필을 가리킵니다. 이제 모든 이름이 그것이 무엇인지 그대로 말해 줍니다.

### 3. 토큰은 계정과 "열려 있는 프로필"을 담고, 회사 전환은 세션을 교체한다

**목표:** 토큰은 *누가 로그인했는지*와 *어느 회사가 열려 있는지*를 말해야 합니다. 그리고 회사를 바꿀 때 비밀번호를 다시 묻지 않아야 합니다.

**선택지:**
- 회사마다 토큰을 따로 두어, 앱이 세션 여러 개를 관리한다.
- 소속된 모든 회사 목록을 토큰에 담는다.
- **로그인 하나에 세션 하나, 열려 있는 프로필만 토큰에 담는다.**

**결정:**
```ts
access:  { sub: accountId, pid?: profileId, type: 'access' }   // pid가 없으면 열린 회사 없음
refresh: { sub: accountId, jti, type: 'refresh' }               // DB 행이 열린 프로필을 기억
```
`POST /auth/switch { refreshToken, profileId }`는 기존 리프레시 토큰을 폐기하고, 새 프로필로 새 토큰 쌍을 발급합니다.

**이유:** 토큰에 넣은 회사 목록은 누군가 승인되거나 떠나는 순간 낡은 정보가 됩니다. 세션을 여러 개 두면 로그아웃도 여러 번 해야 합니다. 어떤 프로필이 열려 있는지 *기억하는* 세션 하나라면, 갱신할 때는 있던 회사가 유지되고, 전환은 교체를 한 번 더 하는 것일 뿐입니다.

가드에는 규칙 두 개가 새로 생겼습니다.
- **이 계정의** 프로필이 아닌 `pid`는 401입니다. 위조되었거나 낡은 토큰이 다른 사람 행세를 하면 안 되니까요.
- 열린 회사가 없는 토큰으로 회사가 필요한 라우트를 부르면 **403 `Choose a company first`** 입니다. 서비스 깊숙한 곳에서 호출자가 없어 500이 나는 것보다 훨씬 낫습니다.

회사 없이도 동작하는 라우트(`/auth/me`, `/devices`, 로그인 수단)에는 `@AccountRoute()`를 붙였습니다. 가드는 `@Public()`을 읽을 때와 똑같은 방식으로 이 메타데이터를 읽습니다.

**결과:** 로그인하면 앱은 회사 드롭다운과 열 프로필(마지막으로 전환한 곳, 없으면 가장 최근 것)을 함께 받습니다. 회사 전환은 요청 한 번이면 되고, 비밀번호는 필요 없습니다.

### 4. 회원가입은 로그인만 만든다

**목표:** 지금까지 계정 만들기와 회사 합류는 늘 요청 하나(`register`, `register/member`)였습니다. 한 사람이 여러 회사에 속하게 되면 이 둘은 별개의 행동입니다.

**결정:** `POST /auth/signup { phone, phoneVerificationToken, credentials }`는 계정과 첫 로그인 수단을 만들고, **그 외에는 아무것도** 만들지 않습니다. 프로필도, 회사도 없습니다. 응답은 `profile: null, companies: []`이고, 앱은 "합류하거나 만들기" 화면으로 갑니다.

작은 디테일 하나가 긴 공부로 이어졌습니다(TIL 참고). credentials는 `{ type: 'password', … } | { type: 'social', … }` 형태의 유니온인데, 저는 태그가 **대소문자를 가리지 않기를**(`'Social'`, `'PASSWORD'`) 바랐습니다. class-transformer의 `discriminator` 옵션으로는 안 됩니다. 정확히 일치하는지만 보고, 그것도 `@Transform`이 돌기 전의 *원본* JSON에서 보기 때문입니다. 그래서 태그를 소문자로 바꾼 사본을 보고 클래스를 고르는 `@Type` **타입 함수**를 쓰고, 작은 `@LowercaseTag()`가 `@Equals`를 위해 태그를 소문자로 저장하게 했습니다.

**결과:** 열린 회사가 없는 세션에 이르는 첫 API 경로가 생겼습니다. 덕분에 결정 3의 "Choose a company first" 403이 드디어 e2e 테스트를 갖게 됐습니다.

### 5. 합류: 판단은 인덱스에게, 무작위 대입엔 브레이크를

**목표:** `POST /me/companies/join { joinCode, name }`은 승인 대기 중인 프로필을 만듭니다. 같은 회사에 두 번 합류하면 실패해야 하고, 두 요청이 같은 순간에 와도 마찬가지입니다. 그리고 8자리 코드(1억 가지)는 무작위 대입으로 맞힐 수 없어야 합니다.

**결정:**
- **중복:** "이미 멤버인가?"를 먼저 확인하지 않습니다. 부분 유니크 인덱스가 정합니다.
  ```prisma
  @@unique([accountId, companyId], where: raw("((deleted_at IS NULL) AND (status <> 'DEACTIVATED'::profile_status))"))
  ```
  `createManyAndReturn({ skipDuplicates: true })`는 삽입하거나 `[]`를 돌려주고, `[]`면 409입니다. 동시에 들어와도 Postgres가 딱 하나만 통과시킵니다.
- **무작위 대입:** **틀린** 코드는 하나하나 `company_join_attempts`에 행으로 남습니다. 최근 한 시간 안에 다섯 행이면 429입니다. 정각에 초기화되는 게 아니라 *지금부터 거슬러 한 시간*을 보는 롤링 윈도라서, 정각을 기다리는 꼼수가 통하지 않습니다. 이 개수 확인은 코드를 조회하기 **전에** 하기 때문에, 막힌 계정은 아무것도 알 수 없습니다. 여섯 번째로 넣은 코드가 맞았다는 사실조차요. 맞는 코드는 행을 남기지 않습니다.

**이유, 그리고 함정:** 틀린 시도의 행은 **404가 나도 살아남아야** 합니다. 트랜잭션 안이었다면 예외가 행을 롤백해 버려서 브레이크가 절대 걸리지 않습니다. 그래서 코드 조회와 시도 기록은 트랜잭션 **밖에서**, 문장마다 따로 커밋되게 했습니다.

**결과:** 동시에 두 번 합류하면 201 하나와 409 하나가 나옵니다. 틀린 코드 다섯 번은 404, 여섯 번째 시도는 맞는 코드로도 429입니다. 다른 계정에는 영향이 없습니다. 시도 테이블의 인덱스는 `account_id` 하나가 아니라 `(account_id, created_at)`이라서, 개수를 셀 때 공격자의 전체 이력이 아니라 많아야 인덱스 항목 다섯 개만 읽습니다(TIL 참고).

### 6. 회사 만들기: 먼저 잠그고, 그다음 센다

**목표:** `POST /me/companies`는 회사와 승인 대기 중인 OWNER 프로필을 만듭니다. 단, **계정 하나당 승인 대기 중인 회사는 최대 하나**입니다(제가 정한 규칙: 한 계정이 관리자에게 등록 신청을 쏟아붓지 못하게).

**선택지:** "대기 중**이면서** OWNER 역할인 행은 최대 하나"는 유니크 인덱스로 표현할 수 없습니다. 역할이 다른 테이블에 있으니까요. 단순히 개수만 세면 경합이 생깁니다. 동시에 두 번 만들면 둘 다 0을 세고, 둘 다 만듭니다.

**결정:** 쓰기로 잠그고, 그다음 셉니다.
```ts
await transaction.account.updateMany({ where: { id: accountId }, data: { updatedAt: new Date() } }); // 행 잠금을 건다
const waiting = await transaction.profile.count({ where: { accountId, status: 'PENDING_APPROVAL', role: { code: 'OWNER' } } });
```

**이유:** `UPDATE`는 트랜잭션이 끝날 때까지 그 계정 행에 잠금을 걸어 둡니다. 그래서 두 번째 요청은 같은 줄에서 기다립니다. Postgres의 기본 격리 수준인 READ COMMITTED에서는 각 문장이 *자기가 시작되기 전*에 커밋된 내용을 모두 봅니다. 그래서 기다리던 요청의 count는 첫 번째가 커밋된 뒤에 돌아 회사 하나를 보고, 409로 답합니다. **순서가 핵심입니다.** count를 먼저 하면 둘 다 0을 읽습니다. 유닛 테스트가 잠금이 count보다 먼저인지 확인합니다.

나머지는 익숙한 패턴입니다. 회사 행은 만든 사람이 필요하고 프로필은 회사가 필요하니, 프로필을 먼저 `companyId: null`로 넣습니다. 이미 등록된 사업자번호면 트랜잭션 **안에서** 예외를 던져, 반쯤 만들어진 OWNER 프로필까지 롤백합니다. 롤백이 없다면 그 고아 프로필 때문에 이후의 모든 회사 만들기가 영원히 409가 됩니다.

**결과:** 버튼을 두 번 눌러도 201 하나와 409 하나입니다. 서로 다른 계정은 서로 다른 행을 잠그니 나란히 진행됩니다.

### 7. 회사마다 이름과 연락용 이메일, 이메일은 코드로 증명

**목표:** 회사마다 나를 부르는 이름과 연락용 이메일을 따로 두고, 그걸 내가 직접, 지금 열려 있는 회사에 대해서만 바꿀 수 있게 하기.

**결정:**
- `PATCH /profiles/me { name }`와 `PUT /profiles/me/contact-email { email, emailVerificationToken }`.
- "me"는 토큰에 열려 있는 프로필이고, 클라이언트가 보낸 id는 절대 쓰지 않습니다.
- 권한 데코레이터가 없어서 **아직 승인 대기 중인** 프로필도 이메일을 설정할 수 있습니다. 그래야 "승인되었습니다" 이메일이 갈 곳이 생기니까요.

**이메일에 증명이 필요한 이유:** 증명되지 않은 주소를 받으면 오타 하나에 모든 알림이 조용히 사라지고, 남의 주소를 넣으면 회사 공지가 새어 나가고, 피해자의 주소를 넣으면 알림이 스팸 대포가 됩니다. 증명은 기존 이메일 코드 흐름에서 받습니다. **그 주소에 묶여 있고 한 번만 쓸 수 있으며**, 저장과 같은 트랜잭션에서 소비되기 때문에 잘못된 증명으로는 아무것도 저장되지 않습니다.

**작은 방어 하나:** Express는 등록된 순서대로 라우트를 맞춰 보고, `:id`는 `me`라는 글자에도 맞습니다. 그래서 `MyProfileController`를 `/profiles/:id/...` 라우트를 가진 컨트롤러보다 **먼저** 등록하고, 유닛 테스트가 모듈 메타데이터를 읽어서 이 순서를 지킵니다.

**결과:** 파트타이머는 한 브랜드에서는 "Lee", 다른 브랜드에서는 "Lee Ji-eun"일 수 있고, 각자 업무용 이메일을 따로 둘 수 있습니다.

### 8. 폰 하나로 모든 회사의 푸시를

**목표:** 기기는 계정에 속하므로, 어느 회사가 열려 있든 폰 하나가 모든 회사의 푸시를 받습니다. 잠금 화면에서는 어느 회사 알림인지 보여야 하고, 누르면 맞는 회사가 열려야 합니다.

**결정:** 모든 푸시에 다음이 붙습니다.
```ts
title: `${company.name} · ${subject}`
data:  { ...eventData, profileId: recipient.id, ...(recipient.company ? { companyId } : {}) }
```
- **`profileId`** 가 들어가는 건 `POST /auth/switch`가 프로필을 받기 때문입니다.
- 받는 사람의 id를 **마지막에** 펼쳐서, 이벤트 데이터에 같은 이름의 키가 있어도 받는 사람 쪽이 이깁니다.
- 회사가 없는 플랫폼 관리자는 이벤트 원래의 제목과 데이터를 그대로 받습니다.

**추가 비용이 없는 이유:** `notifyProfiles`는 기기를 찾으려고 이미 받는 사람들을 조회하고 있었습니다. 관계 select 하나로 회사가 따라옵니다.
```
받는 사람마다 회사를 하나씩 조회:     1 + N개 쿼리 (5명 → 6개)
select: { company: { select: … } }:  N이 얼마든 쿼리 2개
```

**결과:** 잠금 화면에 "Acme · 새 발주가 등록되었습니다"가 뜨고, 누르면 먼저 Acme로 전환됩니다.

### 9. 축소 단계: 모든 테스트가 쓰던 엔드포인트를 걷어내다

**목표:** `POST /auth/register`와 `/auth/register/member`를 삭제하기. 다섯 태스크 동안 옛 경로와 새 경로가 나란히 살았던 expand → migrate → contract의 *contract*입니다.

**남겨 두지 않고 지운 이유:** 경로가 둘이면 앞으로 생길 모든 규칙을 두 번 만들어야 합니다. 게다가 옛 경로는 새 경로가 지키는 규칙을 조용히 어기고 있었습니다. 비밀번호 `register`는 로그인 이메일을 **증명 없이** 연락용 이메일로 복사했으니까요. 아직 프로덕션이 없으니 유예 기간도 필요 없었습니다.

**방법:** 진입점을 지우고 `tsc`가 모든 참조를 나열하게 했습니다. 그다음, 에러는 안 나지만 이제 아무도 안 쓰는 것들을 *검색*했습니다. `AuthService` 생성자의 의존성 두 개, 모듈 import 하나, DTO 클래스 하나, 그리고 데코레이터를 딱 하나만 만들게 된 팩토리였습니다.

**의외의 발견:** 모든 e2e 스위트가 `register`로 오너와 멤버를 만들면서, 그 증명 없는 복사 덕분에 **연락용 이메일을 공짜로 얻고 있었습니다.** 새 흐름에서는 증명하기 전까지 아무도 연락용 이메일이 없으니, 이메일을 확인하는 스위트는 전부 실패했을 겁니다. 새 공용 헬퍼 `suiteAccounts(app, naming)`은 스위트마다의 이름 규칙을 클로저로 기억하는 팩토리이고, `{ contactEmail: true }` 옵션을 받습니다. 이 옵션은 Mailpit을 거치는 **실제** 증명 흐름을, 실제 사람과 같은 순서로 승인 *전에* 실행합니다. 컬럼에 직접 쓰면 더 빨랐겠지만, 방금 만든 규칙을 바로 건너뛰는 셈이었을 겁니다.

**결과:** 16개 스위트를 다시 썼습니다. 그중 9개는 기계적인 작업이었습니다. 모두 같은 설정 헬퍼 두 개를 거의 똑같이 복사해 두고 있었는데, 그 복사본이 이제 공용 파일 하나가 됐습니다. 그리고 새 **파트타이머 시나리오**가 설계 전체를 처음부터 끝까지 걸어 봅니다.
1. A에 합류해 승인받고, B에 합류 신청(A는 계속 동작);
2. B가 승인하고, Park이 B로 전환;
3. 각 회사의 토큰은 상대 회사 멤버를 조회하면 404;
4. 승인 푸시 두 개가 같은 폰에 오고, 각자 자기 `profileId`를 담음;
5. 로그아웃하면 둘 다 끝남;
6. 떠난 회사는 드롭다운에서 사라짐.

267개 테스트가 첫 실행에서 모두 통과했습니다.

### 10. 후속 작업: 합류할 때 이메일 증명까지 *함께*

**목표:** 옛 경로가 사라지자, 신규 가입자는 승인 이메일을 받기까지 다섯 번을 호출해야 했습니다. 저는 한 번이면 되길 바랐습니다. 이미 증명한 주소를 들고 합류하거나 회사를 만드는 것.

**결정:** 선택 사항인 한 쌍, `contactEmail` + `emailVerificationToken`. **둘 다 보내거나, 둘 다 안 보내거나**이고, 두 DTO가 함께 상속하는 작은 기반 클래스에 둡니다.
```ts
const sendsEither = (dto) => dto.contactEmail !== undefined || dto.emailVerificationToken !== undefined;

@ValidateIf(sendsEither) @Transform(normalizeEmail) @IsEmail()      contactEmail?: string;
@ValidateIf(sendsEither) @IsString() @IsNotEmpty()                  emailVerificationToken?: string;
```
조건이 거짓이면 그 필드의 규칙을 모두 건너뜁니다. 둘 중 하나라도 오면 두 필드를 모두 검사하므로, 반쪽만 보내면 빠진 필드를 짚는 400이 됩니다.

**재미있는 부분:** 합류에는 일부러 트랜잭션을 **두지 않았었습니다**(결정 5). 이제는 증명과 프로필을 함께 저장해야 합니다. 그래서 트랜잭션을 코드 조회 **다음에** 시작합니다. 틀린 코드의 행은 여전히 404 뒤에도 살아남고, 중복 합류의 409는 *안에서* 던지므로 거절된 합류가 증명을 낭비하지 않습니다.

**결과:** 미리 알려 준 주소로 승인 이메일이 오고, e2e 271개가 통과합니다.

## TIL (오늘 배운 것)

**"discriminator? `credentials.type`을 보고 클래스를 고르는 건가?"**
네. `@Type` 옵션에 직접 적는 조회 표입니다. `property: 'type'`에 `subTypes: [{ name: 'social', value: SocialDto }, …]`를 붙이는 식이죠. class-transformer는 그 키를 **원본 JSON에서** 읽어 이름과 **정확히** 맞춰 보고, 맞는 게 없으면 `@Type(() => …)` 화살표 함수가 돌려주는 클래스로 대신합니다. 그래서 `'Social'`은 아무 말 없이 비밀번호 클래스가 됐던 겁니다.

**"`keepDiscriminatorProperty: true`는 왜?"**
기본 동작은 클래스를 고른 뒤 라벨을 지우는 것입니다. 라이브러리는 객체의 클래스 자체를 라벨로 보기 때문에, 다시 JSON으로 바꿀 때 같은 표를 거꾸로 읽어 라벨을 써 넣습니다. 우리 클래스는 `type`을 *직접 선언*하고 `@Equals`로 검사하며, 서비스도 그 값으로 분기하니 남겨 둬야 했습니다.

**"`@Type`이 전체적으로 하는 일은?"**
`ValidationPipe`는 라이브러리 두 개를 차례로 돌립니다. class-transformer가 **만들고**(`plainToInstance`), class-validator가 **검사**합니다(`validate`). JSON에는 클래스가 없는데 규칙은 클래스에 붙어 있으니, 중첩 객체를 어떤 클래스로 만들지 누군가 정해 줘야 합니다. `@Type`이 그 결정입니다.
- `@Type(() => X)`는 항상 `X`를 만들고, 배열이면 원소마다, `Number`나 `Date`면 변환합니다.
- `@Type((options) => …)`는 직접 결정하는 함수로, 부모 JSON 전체를 받습니다.
- `@Type(() => Fallback, { discriminator })`는 조회 표에, 내 클래스를 대체값으로 둔 것입니다.

그다음 `@ValidateNested()`가 안으로 들어가 그 클래스의 규칙을 돌립니다.

**"그럼 클래스를 고르려면 `@Transform`이 아니라 `@Type`이어야 한다는 거지? `@Transform`은 뭘 하는데?"**
`@Transform`은 **값**을 바꾸고, 그 필드가 만들어진 **뒤에** 돕니다. `@Type`의 함수는 만들기 **전에** 돌고 **클래스**를 돌려줍니다. 어떤 `@Transform`이 credentials를 볼 때쯤이면 클래스는 이미 정해져 있습니다. 태그를 소문자로 바꾸는 `@Transform`은 심지어 고르려는 *그 클래스 안에* 붙어 있고요.

**"우리 credentials에서 `object`, `property`, `newObject`는 각각 뭐지?"**
- `object`는 요청 본문 원본 전체입니다(전화번호엔 아직 하이픈이 있고, 태그도 아직 `'Social'`).
- `property`는 `'credentials'`입니다.
- `newObject`는 반쯤 만들어진 DTO로, 지금까지 끝난 필드만 들어 있어서 JSON의 키 순서에 따라 달라집니다.

그래서 고르는 함수는 `object[property].type`을 읽고 `newObject`는 무시합니다.

**"credentials DTO가 왜 세 개나?"**
비밀번호는 어디서나 같습니다. 소셜은 모양이 두 가지 필요했습니다. register는 프로필을 만들었으니 증명된 연락용 이메일을 들고 다녔고, signup은 프로필을 안 만드니 티켓만 가진 클래스를 두어서, 엉뚱하게 들어온 `contactEmail`을 조용히 무시하지 않고 화이트리스트로 거절하게 했습니다. 축소 단계를 거친 지금은 두 개만 남았습니다.

**"인덱스를 왜 `account_id` 하나가 아니라 `(account_id, created_at)`으로?"**
인덱스는 정렬된 목록입니다. `account_id`만 있으면 Postgres는 그 계정의 행을 찾긴 하지만, 시간을 보려면 하나하나 열어 봐야 합니다. 시도 테이블은 정리되지 않고 계속 쌓이고요. 시간을 두 번째 컬럼으로 두면 "한 시간 전"으로 바로 뛰어가 계정이 바뀔 때까지만 읽습니다. 많아야 다섯 개입니다. 같음(`=`) 조건 컬럼을 앞에, 범위 조건 컬럼을 뒤에 둡니다.

**"`create()`를 전체 맥락과 함께 설명해 줘."**
결정 6이 그 답입니다. 이해가 확 된 건 "각 단계가 없으면 무엇이 잘못되는가"를 물었을 때였습니다. 잠금이 없으면 버튼 두 번에 대기 중인 회사가 둘 생기고, 트랜잭션 안에서 예외를 안 던지면 고아 오너 프로필이 이후의 모든 회사 만들기를 막습니다.

**"오너가 아직 승인하지 않아서 역할을 안 돌려주는 거야?"**
서로 다른 두 가지입니다. `/profiles/me`는 원래 역할을 돌려주지 않습니다. 자기가 수정하는 필드만 답하니까요. 드롭다운에서 **합류한** 프로필의 역할은 승인자가 고를 때까지 `null`이지만, 회사를 **만든** 사람은 처음부터 OWNER입니다. 관리자의 승인은 회사를 활성화할 뿐 역할을 바꾸지 않습니다.

**"N+1이 뭐고, 관계 select는 무엇을 해결하지?"**
N개 행을 가져오는 쿼리 하나에, 행마다 쿼리를 하나씩 더 날리면 왕복이 1 + N번이 되고 N에 비례해 늘어납니다. 보통은 반복문 안의 헬퍼 속에 숨어 있죠. 관계 select는 원하는 결과의 모양을 적는 것입니다. 저는 Prisma가 "같은 쿼리에서 조인한다"고 설명했는데, 쿼리 로그를 찍어 보니 틀렸습니다. 기본 동작은 쿼리 **두 개**입니다. 부모를 가져오고, 자식을 `WHERE id IN (…)`으로 한꺼번에 가져와 메모리에서 붙입니다. 이점은 JOIN이 아니라 쿼리 수가 더는 늘지 않는다는 데 있습니다. (기존 코드에서도 작은 N+1을 하나 발견했습니다. `notifyProfiles`의 이메일 쪽이었습니다.)

**"승인되면 이메일로 알려 줄 수 있어?"**
네, 대기 중인 프로필이 먼저 연락용 이메일을 설정해 두면요. 푸시는 아무것도 필요 없습니다. 기기는 계정에 속하니까요. 이 질문이 후속 작업(결정 10)이 됐습니다.

**"내 터미널을 그냥 읽을 수는 없어?"**
없습니다. 하지만 파일이면 됩니다. `npm run test:e2e 2>&1 | tee e2e.log`. 출력은 그대로 실시간으로 보면서, 로그는 git이 무시하는 파일에 남고, 저는 "다 됐어"라고만 말하면 됩니다.

| 개념 / 라이브러리 | 왜 썼나 |

| `createParamDecorator` | `@CurrentAccount()`, `@CurrentProfile()`이 가드가 채운 `request.account` / `request.profile`을 읽음 |
| 전역 `APP_GUARD` | 요청당 쿼리 하나: 프로필과 그 계정의 `deletedAt`, 또는 계정만 |

| Prisma `updateMany` 잠금 + READ COMMITTED | 계정당 대기 중인 회사 최대 하나 |
| Prisma 관계 select(일괄 `IN` 쿼리) | N+1 없이 모든 푸시에 회사 이름 |
| Prisma `@@index([accountId, createdAt])` | 저렴하게 유지되는 롤링 윈도 개수 세기 |
| `satisfies Prisma.ProfileSelect` + `ProfileGetPayload` | select 상수 하나, 거기서 파생되는 타입 하나 |
| `prisma migrate dev --create-only` + 직접 쓴 SQL | id를 재사용하는 expand → copy → contract, 이름만 바꾸는 마이그레이션 |
| JWT 클레임(`sub`, `pid`, `jti`) + 리프레시 교체 | 열린 프로필을 기억하는, 로그인당 세션 하나 |
| Mailpit + supertest | e2e에서 실제로 이메일로 받은 코드, 받은편지함에서 승인 이메일 확인 |
| Jest `invocationCallOrder` | "잠금 후 count", "삽입 전 증명 소비", "커밋 후 발행"을 테스트로 |

## 마무리

이번 트랙이 만든 것:
- **사람마다 로그인 하나**(`accounts`)와 **회사마다 프로필**(`profiles`). 기존 사용자의 로그인 수단과 기기를 그대로 유지한 채 마이그레이션
- 계정과 열린 프로필을 담은 토큰, **Slack 같은 회사 전환**, 열린 회사가 없을 때의 명확한 403
- **회사 없는 회원가입**, 그리고 `/me/companies`에서 **합류하거나 만들기**. 초대 코드 무작위 대입 브레이크, 계정당 대기 회사 최대 하나
- **회사마다 이름과 코드로 증명한 연락용 이메일**. 합류하거나 회사를 만들 때 미리 증명할 수도 있음
- 폰 하나로 받는 **모든 회사의 푸시**. 각각 어느 회사인지, 어느 프로필을 열지 담음
- 옛 원스텝 `register` 엔드포인트 **퇴역**. 모든 e2e 스위트를 공용 헬퍼로 옮기고, 파트타이머 시나리오로 전체를 검증

간직하고 싶은 교훈: **두 줄의 순서가 곧 설계 전체인 경우가 많다.** 잠그고, 센다. 코드를 조회하고, *그다음* 트랜잭션을 연다. 증명을 쓰고, 삽입하고, 409는 안에서 던진다. 이것들을 거꾸로 써도 대부분의 테스트는 통과합니다. 알아채는 건 실패하도록 작정하고 쓴 테스트 하나뿐입니다.

다음 편: **3부, 떠나기.** 회사 떠나기(프로필이 `DEACTIVATED`가 되어 자리를 비움), 계정 삭제(그리고 애플에게 우리를 잊어 달라고 요청하기. 애플의 필수 요건입니다), 마지막 오너가 떠날 때 회사 닫기. 이건 곧 후임자를 정하는 문제입니다.

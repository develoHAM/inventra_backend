# 세고, 확정하라: 현실과 재고를 맞추는 실사

> Inventra Phase 8 — 두 단계 전에 만든 재고 엔진이 마침내 첫 진짜 호출자를 만나고, *트랜잭션은 누구의 것인가*에 관한 리팩터가 진열대 전체의 대사(reconcile)를 원자적으로 만드는 단계.
> 2026-09-07

## 들어가며

Inventra는 한국의 편집숍/코너 모델을 기반으로 한 멀티테넌트 재고관리 SaaS다 — 회사들이 물리적 매장 안에서 "코너"를 운영한다. Phase 6은 재고를 원자적으로 움직이는 엔진을 만들었고, Phase 7의 재입고 주문은 일부러 그 엔진을 *쓰지 않았다*. Phase 8은 그 엔진이 마침내 진짜 일을 하는 단계다: **재고 실사(inventory audit)** — 물리적 재고 카운트 — 그리고 그것을 시스템에 **적용(apply)**해 숫자를 바로잡는 행위. 흥미로운 지점은 CRUD가 아니었다(이제 그건 주문과 같은 문서 형태다). 그건 apply를 **여러 라인에 걸쳐 한 번에 원자적으로** 만드는 것이었고, 그것이 이전엔 답할 필요 없던 질문의 리팩터를 강제했다: *트랜잭션은 누구의 것인가?*

## 아키텍처 결정들

### 1. 두 단계: 세고, 그다음 적용

**목표.** 매장 관리자가 월말에 하는 일을 모델링하기: 진열대를 돌며 물리적으로 있는 걸 세고, 시스템을 거기에 맞춘다.

**긴장.** 주문(의도만 기록)과 달리, 실사의 *존재 이유 전체*는 장부를 바꾸는 것이다. 그래서 한 번의 행위로 — 세면서 동시에 고치도록 — 만들고 싶어진다. 하지만 장부를 고치는 건 **중대하고 되돌릴 수 없다**: 실시간 잔고를 덮어쓰는 `ADJUSTMENT` 트랜잭션을 쓴다. 사람이 카운트를 — 그리고 그것이 유발할 편차를 — *확정 전에* 보길 원한다.

**선택지.** (a) 실사 생성/확정 시 즉시 대사. (b) 실사는 순수 문서, 대사는 전적으로 수동. (c) **두 단계**: 카운트를 문서로 만들고, 별도의 명시적 *apply*가 확정한다.

**선택.** **(c).** 실사를 `POST`(헤더 + 카운트된 라인)하고, 작업하는 동안 자유롭게 수정하다가, 만족했을 때만 `POST …/audits/:id/apply`. apply는 각 라인을 돌며 그 placement의 `availableQuantity`를 카운트된 숫자로 **설정(set)**하는 `ADJUSTMENT`를 `source = AUDIT`로 찍는다.

**이유.** 두 단계는 "내가 센 것"과 "그대로 만들어라" 사이에 검토 게이트를 둔다. apply 전에 잡힌 오카운트는 값싼 수정이고, apply 후에 잡히면 원장에 교정 트랜잭션이 된다. 그리고 분리는 실사 문서와 그것이 *유발한* 재고 움직임을 별개 기록으로 남긴다 — 실사는 무엇을 셌는지, 원장은 무엇이 바뀌었는지.

**결과.** 실사를 만드는 건 재고를 절대 건드리지 않는다. apply는 교정이 착지하는 단 하나의 의도된 순간이고 — 다음 결정이 보여주듯 — 전부-아니면-전무로 착지한다.

### 2. 트랜잭션은 누구의 것인가? — extract-method 리팩터

**목표.** apply를 **모든 라인에 걸쳐** 원자적으로 만들기. 열 개 placement를 대사하거나 하나도 안 하거나 — 진열대를 절반만 고친 채 두지 않는다.

**장애물.** "N개 쓰기에 걸친 전부-아니면-전무"는 N개 전부를 감싸는 하나의 `$transaction`을 의미한다. 하지만 Phase 6의 `record()`는 **자기 트랜잭션을 소유한다**:
```ts
async record(...) {
  await this.corners.assertWorksCorner(...);      // 가드
  const placement = await ...findFirst(...);      // 가드
  return this.prisma.$transaction((tx) => { ... }); // ← 자기 트랜잭션을 연다
}
```
라인마다 `record()`를 루프 돌리면 N개의 *별개* 트랜잭션이 되고 — 라인 3이 실패하면 라인 1–2는 커밋된 채 남는다. 원자적이지 않다. 그리고 `record()`에 바깥 트랜잭션을 넘겨 합류시킬 수 없다.

**선택지.** (a) `record()` 루프(원자적 아님). (b) `AuditsService` 안에 재고-쓰기 로직 복제. (c) 쓰기를 호출자가 제공한 트랜잭션에서 도는 헬퍼로 **추출**.

**선택.** **(c).** `record()`를 둘로 쪼갰다:
```ts
// 원자적 쓰기 — 호출자가 제공한 tx에서 돈다. 인증 없음, 새 트랜잭션 없음
async recordWithinTransaction(tx: Prisma.TransactionClient, placementId, dto, callerId, source?) { … }

// 단일-쓰기 진입점 — 가드 후, 헬퍼를 감싸는 트랜잭션 하나를 연다
async record(...) {
  await this.corners.assertWorksCorner(...);
  const placement = await ...findFirst(...);
  return this.prisma.$transaction((tx) => this.recordWithinTransaction(tx, placementId, dto, caller.id, source));
}
```
이제 `AuditsService.apply`는 트랜잭션을 **하나** 열고 그 같은 `tx`에서 라인마다 헬퍼를 호출한 뒤 `appliedAt`을 찍는다 — 전부 한 단위로.

**이유.** 트랜잭션이 **파라미터**가 되면서 경계를 호출자가 정한다: 단일 쓰기는 자기 것을 그리고, 배치는 배치 전체를 감싸는 하나를 그린다. DRY이고(원장+잔고 로직이 정확히 한 곳에 산다 — 어긋날 복사본이 없다), 관심사 분리가 깔끔하다: 인가는 호출자의 일, 쓰기는 헬퍼의 일. 그래서 `recordWithinTransaction`엔 `assertWorksCorner`가 *없다* — 실사가 코너를 한 번 인가했으니, 라인마다 재검사는 틀리고 낭비다. 그리고 `record()`의 외부 계약은 그대로라, Phase 6 테스트 8개가 변경 없이 통과한다.

**결과.** apply는 진짜로 원자적이고, `record`가 이미 신뢰한 재고-움직임 의미를 그대로 재사용한다 — 복제 없이.

### 3. apply 시 동결 — 두 상태 기계

**목표.** 적용된 실사가 두 번 적용되거나, 사후 수정되는 걸 막기.

**문제.** apply는 본질적으로 멱등이 아니다 — 다시 돌리면 *두 번째* `ADJUSTMENT` 세트를 쓴다. 그리고 적용된 실사는 특정 시점 카운트의 역사적 기록이다. 사후 수정을 허용하면 원장이 무엇을 셌는지에 대해 거짓말하게 된다.

**선택지.** (a) 상태 추적 안 함 — apply 반복 가능. (b) `appliedAt` 추적, 설정되면 실사 동결.

**선택.** **(b).** apply가 `appliedAt`(+ `appliedByUserId`)을 찍는다. 모든 변경 경로 — 수정, 삭제, apply 자체 — 가 먼저 확인한다:
```ts
if (audit.appliedAt) throw new ConflictException('Audit already applied'); // 409
```

**이유.** 타임스탬프 하나가 실사를 작은 상태 기계로 바꾼다: *미적용*(수정/삭제/적용 가능) → *적용됨*(동결, 불변). 동결된 실사를 재적용/수정/삭제하면 `409` — 조용한 무동작이나 중복 교정이 아니라 명확한 "이 기록은 닫혔다".

**결과.** 실사는 확정되는 순간 불변 아티팩트가 되고, 그것이 만든 원장은 그 카운트의 기록으로 신뢰할 수 있다.

### 4. 자체 권한으로서의 `audits.apply`

**목표.** 누가 재고 교정을 확정할 수 있는지 정하기.

**선택.** `audits.create/read/update/delete`와 분리된 전용 `audits.apply` 권한 — 지금은 전부 같은 역할(OWNER/MANAGER/STAFF)에 가더라도.

**이유.** 세는 것과 *장부에 교정을 확정하는 것*은 같은 사람이 하더라도 개념적으로 다른 권한이다. apply를 자체 권한으로 만들면 RBAC 계층이 "실사를 만들 수 있다"와 "그 교정을 확정할 수 있다"를 구분할 수 있다 — 회사가 교정 승인은 매니저만 하길 원하는 날이 오면, 코드 변경이 아니라 seed 변경이다. 지금 값싸고, 나중에 유연하다.

**결과.** 세기-대-확정 구분이 역할 가정에 묻히지 않고 권한 모델에 명시된다.

## TIL (Today I Learned)

**왜 `record()`를 리팩터하고 `recordWithinTransaction`을 노출했나?**
원자성은 *트랜잭션 경계*에 관한 것이고, `record()`는 자기 것을 그리길 고집했기 때문이다. N개 라인을 전부-아니면-전무로 대사하려면 하나의 트랜잭션이 N개 전부를 걸쳐야 하고 — 그건 쓰기가 *다른 누군가가 연 트랜잭션 안에서* 돌 수 있어야 함을 뜻한다. 추출이 트랜잭션을 파라미터로 만들었다: `record()`는 단일 쓰기용으로 하나를 열고, `apply`는 배치 전체를 감싸는 하나를 열고, 둘은 같은 쓰기 로직을 공유한다. "작업 단위 핸들을 넘겨라" 패턴이다.

**왜 `Promise.all`이 아니라 `for…of` + `await`인가?**
모든 라인-쓰기가 **같은 `tx`**에서 돌고, 하나의 인터랙티브 트랜잭션은 **하나의 DB 연결**에 묶이며, 그 연결은 **한 번에 한 문장**을 처리하기 때문이다. `Promise.all`은 동시성이 없는 연결에 동시에 쏘아붙인다 — 오류나 예측 불가한 직렬화를 내는 알려진 Prisma 지뢰다. 순차 `await`가 "하나의 연결로 한 번에 하나씩"을 존중한다. (트랜잭션 밖, 풀링된 연결에서는 `Promise.all`이 *맞는* 선택이다 — 규칙은 딱: 하나의 `tx` 안에서는 직렬화하라.)

**`POST …/audits/:id/apply`가 RESTful하긴 한가?**
엄밀히는 아니다 — `/apply`는 동사고, 순수 REST는 명사를 원한다. 하지만 이건 실제 API들이 비-CRUD 상태 전이에 쓰는 실용적 "액션 서브리소스" 패턴이다(GitHub `POST …/merge`, Stripe, k8s 서브리소스). "더 RESTful한" 대안들은 *여기선* 더 나쁘다: `PATCH { appliedAt }`로 접으면 그게 무겁고 되돌릴 수 없는 명령이란 걸 숨기고, `POST …/reconciliation`으로 명사화하는 건 대사 결과를 나중에 `GET`할 때만 값어치를 하는데 — 우리 설계상 그렇지 않다. 결과를 조회할 필요가 생기기 전까진 액션 엔드포인트를 유지한다.

**목이 볼 수 없던 버그(또again).** 추출한 헬퍼가 실수로 *자기* `$transaction`을 안에서 열었다 — 그건 실사가 넘긴 `tx`를 무시해, 리팩터의 존재 이유인 원자성을 조용히 깨뜨렸을 것이다. 유닛 테스트는 초록불이었다. 목 처리된 `$transaction`은 그냥 패스스루니까. 그리고 나중에: `@Patch('auditId')` — `:` 빠짐 — 은 리터럴 경로 `…/audits/auditId`에 라우트를 등록해, 진짜 요청이 404 났다. 둘 다 유닛 테스트 157개를 통과해 빠져나갔고 e2e가 잡았다. 목이 눈먼 바로 그 부류 — 트랜잭션 의미와 라우트 배선 — 에서 통합 계층이 제 밥값을 한 게 이걸로 세 Phase째다.

## NestJS 개념 & 라이브러리

| 개념 / 도구 | Phase 8에서 등장한 이유 |
|----------------|------------------------------|
| **추출한 tx-수용 메서드** (`recordWithinTransaction`) | 호출자의 트랜잭션 안에서 원자적 쓰기 재사용; 배치 apply를 전부-아니면-전무로. |
| **`Prisma.TransactionClient`** | 넘겨받는 `tx` 파라미터 타이핑(트랜잭션 중 못 부르는 호출을 뺀 `PrismaClient`). |
| **`$transaction`(인터랙티브) + `for…of await`** | N개 라인-쓰기를 걸치는 하나의 트랜잭션, 단일 연결로 순차 실행. |
| **액션 서브리소스 라우트** (`POST :id/apply`) | 비-CRUD, 부작용 있는 상태 전이 표현. |
| **`@RequirePermissions('audits.apply')`** | 교정 확정을 카운트 편집과 구분하는 전용 권한(총 44). |
| **`PartialType` 수정 DTO** | 부분 `PATCH`는 선택적 필드로 검증해야 함 — 실수로 create DTO를 쓰면 `{ title }` 수정이 400. |
| **크로스-모듈 주입** | `AuditsModule`이 `InventoryModule`을 import해 `InventoryService`를 주입, 쓰기 재사용. |
| **Prisma 관계 `connect`** | 각 카운트 라인의 placement를 복합 유니크로 붙임(Phase 7의 공유-`companyStoreId` 규칙). |

## 마무리

Phase 8은 재고 실사를 내놨다: 풀 CRUD + soft-delete를 갖춘 중첩 `InventoryAudit` + `InventoryAuditItem` 애그리게이트, *세고 그다음 적용*하는 두 단계 흐름, 모든 라인을 하나의 트랜잭션에서 원자적으로 대사하는 apply, 그리고 확정된 실사를 불변 기록으로 바꾸는 동결-온-apply 상태 기계. **유닛 테스트 157개 + e2e 54개, 전부 초록불.**

오래 남을 교훈은 리팩터다. "이 배치를 원자적으로 만들라"는 데이터베이스 관심사처럼 들리지만, *트랜잭션은 누구의 것인가?*라는 설계 질문으로 변했고, 그 답은 쓰기가 트랜잭션을 소유하는 걸 멈추고 그것을 넘겨받게 하는 것이었다. 그 한 수가 복제 로직 한 줄 없이 대사를 원자적으로 만들었고, Phase 6 엔진의 계약을 온전히 남겼다.

**다음 — Phase 9: 구매 예약(purchase reservations).** Phase 6부터 손대지 않은 `reservedQuantity` 버킷이 있고, 세 번째 `TransactionSourceType` — `RESERVATION` — 이 호출자를 기다린다. 예약은 그 버킷에 대해 고객을 위한 재고를 잡아두고, 이행이나 취소가 그것을 움직인다. 이번 Phase에 마침내 돈 엔진이 곧 재고를 움직이는 것만이 아니라 *잡아두는* 법을 배운다.

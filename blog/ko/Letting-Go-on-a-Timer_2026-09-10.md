# 타이머에 맞춰 놓아주기

> Inventra Phase 10a — 스케줄된 잡이 아무도 찾으러 오지 않은 홀드를 마침내 풀어주고, cron이 알고 보니 같은 서비스로 들어가는 또 하나의 정문일 뿐인 단계.
> 2026-09-10

## 들어가며

Inventra는 한국의 편집숍/코너 모델을 기반으로 한 멀티테넌트 재고관리 SaaS다 — 회사들이 물리적 매장 안에서 "코너"를 운영한다. Phase 9는 엔진에게 고객을 위해 재고를 *잡아두는* 법을 가르쳤지만, 일부러 실 하나를 늘어뜨려 뒀다: 예약은 `expiresAt`을 가질 수 있었지만, 아무것도 그것에 대해 행동하지 않았다. 고객이 다시 찾으러 오지 않은 홀드는 영원히 거기 앉아, 재고를 진열대에서 조용히 빼놓는다. Phase 10a는 그 루프를 닫는다 — 만료된 홀드를 쓸어 풀어주는 백그라운드 잡 — 그리고 그 과정에서 이것은 HTTP 요청으로 트리거되지 않는 앱의 첫 조각이다. 그리고 적어둘 만한 두 개의 인프라 우회로가 딸려 왔다.

## 아키텍처 결정들

### 1. Claim-then-release — 락 없이 안전하게

**목표.** `expiresAt`이 지난 모든 `RESERVED` 홀드를, 절대 이중 해제 없이 풀어주기.

**위험.** 백그라운드 스윕은 경쟁 상태의 전형적 무대다. 앱 인스턴스를 둘 배포하면 각자 자기 cron을 돌리므로, 둘 다 같은 분에 스윕을 발사하고 둘 다 같은 만료 예약을 본다. 순진한 "만료된 것 찾아, 각각 풀기"는 같은 홀드를 두 번 푼다 — `reserved -= q` 두 번, `available += q` 두 번 — 버킷을 오염시킨다. 스윕과 그 순간 고객이 이행/취소하는 것 사이에도 같은 경쟁이 존재한다.

**선택지.** (a) read-then-release (경쟁). (b) 분산 락(Redis / Postgres advisory lock)으로 스위퍼 하나만 돌게. (c) **가드된 클레임** — 먼저 원자적으로 `RESERVED → EXPIRED`를 뒤집고, *내가* 뒤집은 경우에만 푼다.

**선택.** **(c).** 각 예약은 자기 트랜잭션 안에서 클레임되고 풀린다:
```ts
const { count } = await tx.purchaseReservation.updateMany({
  where: { id: reservation.id, status: 'RESERVED' },   // 클레임
  data: { status: 'EXPIRED', expiredAt: now },
});
if (count === 0) return false;                          // 누군가 먼저 가져감 — 스킵
await inventory.recordWithinTransaction(tx, /* RESERVATION_RELEASE … */);
```

**이유.** 이건 Phase 6의 바로 그 가드된-`updateMany` 철학을, 재고 버킷 대신 상태 컬럼에 겨눈 것이다. 클레임은 단일 원자적 쓰기다: 두 스윕(혹은 스윕과 이행)이 경쟁하면, 하나가 `RESERVED → EXPIRED`를 뒤집고 `count: 1`을 얻고, 다른 하나는 아무것도 매칭 못 해(`status`가 더는 `RESERVED`가 아님) `count: 0`을 얻어 해제를 스킵한다. 분산 락도, 조율도 없다 — 정확성이 하나의 조건부 쓰기에서 떨어져 나온다. 그리고 각 예약이 `try/catch`로 감싼 자기 트랜잭션을 가지므로, 나쁜 행 하나는 스윕을 멈추는 대신 로그 남기고 스킵된다.

**결과.** 하나를 돌리든 열을 돌리든 정확한 스윕이, 앱이 이미 가진 프리미티브로 지어졌다.

### 2. 엔진의 네 번째 호출자 — 해제는 해제다

**목표.** 홀드가 만료되면 재고를 옮기기.

**선택.** 스윕은 자기만의 재고 로직을 발명하지 않는다 — `InventoryService.recordWithinTransaction`을 `RESERVATION_RELEASE`로 호출한다. 수동 취소가 쓰는 것과 같은 effect, `source = RESERVATION`으로 찍고. 그저 스윕 자신의 트랜잭션을 넘길 뿐이다.

**이유.** 만료 *가* 해제다 — 재고 움직임은 취소와 동일하고, 트리거만 다르다. 엔진을 재사용하면 원장, 버킷 산술, 가드된 감소가 전부 공짜로 오고, `reserved → available` 이동이 정직하게 기록된다. 이것은 그 추출된 헬퍼의 네 번째 별개 호출자이며(`record`, 감사 apply, 예약 create/fulfill/cancel 다음), Phase 8에서 원자적 쓰기를 `record`에서 뽑아낸 게 옳았다는 가장 명확한 증거다.

**결과.** 완전히 새로운 생명주기 이벤트에 재고-움직임 코드 제로.

### 3. 시스템의 행동은 누구의 행동인가?

**목표.** 원장의 `createdByUserId`는 필수 필드인데, cron에는 로그인한 사용자가 없다.

**선택.** 해제를 `reservation.createdByUserId`에 — 예약을 만든 사람에게 — 귀속.

**이유.** 전용 "시스템 사용자"나 핵심 원장의 nullable `createdByUserId`는 이론적으로 둘 다 더 깔끔했지만, 가장 중심 테이블에 스키마나 seed 변경을 요구했다. 창작자에게 귀속하면 둘 다 필요 없고, 맥락상 오해를 부르지도 않는다: 트랜잭션은 `source = RESERVATION`을 달고 예약 상태는 `EXPIRED`라, 둘이 합쳐 "시스템이 이 홀드를 자동 만료시켰다"로 명확히 읽힌다, "이 사용자가 수동으로 풀었다"가 아니라. `source` + 종료-상태 쌍이 이미 *무슨 일이 일어났는지*를 인코딩한다; 창작자는 그저 *누구의 예약이었는지*에 답한다.

**결과.** 정직-한-정도의 행위자로 기록된 시스템 행동, 원장 모양 변경 없이. (`fulfilledAt`/`cancelledAt`과 맞추려고 대칭적 `expiredAt` 컬럼을 추가했다 — 이번 Phase의 유일한 작은 스키마 변경.)

## TIL (Today I Learned)

**NestJS 스케줄러가 실제로 내 다른 서비스들과 어떻게 함께 동작하나?** 그냥 또 하나의 진입점이다. `ScheduleModule.forRoot()`가 부팅 때 모든 provider를 스캔해 `@Cron` 태그된 메서드를 찾고, 각각을 **그 실제 싱글톤 인스턴스에서** 호출하는 타이머를 등록한다 — 그래서 `sweepExpired()` 안에서 `this.prisma`와 `this.inventory`는 모든 컨트롤러와 서비스가 쥔 것과 같은 주입된 인스턴스다. cron은 HTTP 서버의 동료다: HTTP 요청은 `guard → controller → service`로 가고, cron은 `timer → 서비스 메서드`로 곧장 간다. 둘 다 같은 싱글톤에 같은 방식으로 닿는다. `@Cron` 데코레이터는 "언제 이걸 자동 호출할지"의 메타데이터일 뿐이다; 메서드는 평범한 `async` 메서드다 — 바로 그래서 테스트가 타이머 없이 `app.get(ReservationExpiryService).sweepExpired()`를 그냥 호출할 수 있다.

**왜 `due.length`를 쓰지 않고 루프 안에서 `released`를 세나?** 후보 *인 것*과 해제 *되는 것*이 같지 않기 때문이다. `due`는 조회 시점에 만료돼 보인 모든 것; 가드된 클레임이 그다음 이기거나(`count: 1`, 해제) 동시 액션에 지거나(`count: 0`, 스킵) 한다. 그래서 `due.length`는 과다 계산한다 — 다른 스윕이나 이행이 이미 처리한 것을 포함하니까. `releasedCount`는 실제 해제만 집계하는데, 그게 로그하고 단언할 정직한 숫자다. 정확성이 아니라 리포팅이다: 재고는 세든 안 세든 똑같이 움직인다.

**`prisma generate` 대 버전 불일치.** Phase 도중 `prisma` CLI를 `8.0.0-rc`로 올렸는데 `@prisma/client`는 7에 머물렀다. `npx prisma generate`는 여전히 그 명령이다 — 하지만 CLI와 클라이언트는 **같은 메이저**여야 한다, CLI가 런타임이 이해해야 하는 클라이언트를 생성하니까. CLI 8 + 클라이언트 7은 에러 나거나 v7 런타임이 못 읽는 클라이언트를 낸다. 해법은 CLI를 v7으로 되돌려 클라이언트·어댑터에 맞추는 것. 교훈: Prisma 패키지 하나의 메이저 범프는 전부의 범프다, 의도적으로 하는 것 — Phase 도중의 곁길이 아니고, 릴리스 후보에서는 결코.

**cron 추가가 왜 e2e를 깼나 (그리고 왜 유닛과 e2e가 반대 설정을 필요로 하나)?** `@nestjs/schedule` v12는 **ESM 전용**(`"type": "module"`)이다. **유닛** 러너는 순수 CommonJS Jest라, 패키지의 `export` 구문에 질식한다 — 그래서 패키지를 CJS로 *변환*하는 `transformIgnorePatterns`가 필요하다. **e2e** 러너는 이미 `--experimental-vm-modules` 하에 돈다(Prisma 7의 WASM 쿼리 컴파일러가 필요로 함) — ESM 컨텍스트인데, 거기서 패키지를 CJS *로* 변환하면 그 `exports`가 undefined가 된다. 그래서 e2e는 반대로 해야 한다: 변환하지 **않고**, Jest의 ESM 로더가 네이티브 ESM을 import하게. 같은 의존성, 두 러너, 두 반대 해법 — 한 러너는 CJS고 다른 하나는 ESM이니까.

## NestJS 개념 & 라이브러리

| 개념 / 도구 | Phase 10a에서 등장한 이유 |
|----------------|------------------------------|
| **`@nestjs/schedule`** (`ScheduleModule.forRoot`, `@Cron`, `CronExpression`) | `sweepExpired()`를 매분 백그라운드 잡으로 실행. |
| **동료 진입점으로서의 스케줄러** | cron은 평범한 DI로 서비스에 닿는다 — 요청 없음, 가드 없음, 사용자 없음(그래서 행위자 + 가드된-클레임 결정들). |
| **가드된 `updateMany` 클레임** | Phase 6의 원자적-쓰기 트릭을 상태 컬럼에 적용 — 락 없이 멀티-인스턴스 안전. |
| **`recordWithinTransaction`** | 엔진의 네 번째 호출자; 해제는 해제다. |
| **ESM 전용 의존성 + Jest** | 유닛(CJS)은 `@nestjs/schedule`을 CJS로 변환; e2e(`--experimental-vm-modules`의 ESM)는 네이티브로 로드. |
| **Prisma 패키지 버전 정렬** | CLI, `@prisma/client`, `@prisma/adapter-pg`가 메이저를 공유해야 함. |

## 마무리

Phase 10a는 스케줄된 자동 만료 스윕을 내놨다: 가드된 쓰기로 각 만료 홀드를 클레임하고 다른 모든 움직임이 쓰는 같은 엔진으로 재고를 푸는 `@Cron` 잡, 동시 인스턴스 하에서도 안전하고, 원장에 정직하게 귀속된. **유닛 테스트 170개 + e2e 63개, 전부 초록불** — ESM과 Prisma 버저닝 먼지가 가라앉은 뒤에.

개념적 수확은 인프라 교훈보다 작았다. 스윕 자체는 쓰기가 거의 지루했다, 어려운 부분들 — 원자적 쓰기, 가드된 감소, 해제 effect — 이 이미 존재했으니까; cron은 낡은 기계에 배선된 새 시계일 뿐이다. 진짜 배움은 운영적이었다: 스케줄러가 같은 DI 그래프로의 또 다른 트리거에 지나지 않는다는 것, 그리고 ESM 전용 의존성을 CommonJS-와-WASM 툴체인에 끌어들이는 게 실제 오후가 사라지는 곳이라는 것.

**그리고 그게 도메인, 완성이다.** 인증, 인가, 카탈로그, 매장, 코너, 배치, 트랜잭션, 주문, 감사, 예약, 그리고 이제 그것들 뒤를 치우는 잡까지 — Inventra는 상품을 코너 진열대에서의 전 생애에 걸쳐 나를 수 있다. 남은 건 일부러 *아직* 짓지 않은 것: 캐싱, 레이트 리미팅, 메트릭, API 문서 — 실제 배포가 실제 이유를 줄 때 더하는 횡단 관심사들이지, 그 전이 아니다. 엔진은 잡고, 움직이고, 대사하고, 이제 놓아준다. 그건 완성된 기계다.

# 현관문은 넷, 자물쇠는 하나

> "카카오·구글·페이스북·애플로 로그인" 기능을 붙였습니다. 어려웠던 건 제공자 연동이 아니었습니다. 서버가 무엇을 믿어야 하는지 정하는 일, 그리고 모든 경합의 최종 판정을 제 코드가 아닌 데이터베이스에 맡기는 일이었습니다.

*2026-11-03*

## 들어가며

[Inventra](https://github.com/develoHAM/inventra_backend)는 **NestJS 11 + Prisma 7 + PostgreSQL**로 만드는 멀티테넌트 재고 관리 SaaS입니다. 한국의 백화점 입점 매장 구조를 모델로 삼았습니다. 회사들이 매장 안에 "코너"를 운영하고, 오너·매니저·스태프가 재고를 함께 관리합니다.

이번 트랙에서는 **네 개 제공자의 소셜 로그인**을 붙였습니다. 카카오, 구글, 페이스북, 애플입니다. 모바일 앱(React Native / Expo)은 각 제공자의 **네이티브 SDK**를 씁니다. 버튼을 누르면 카카오톡이나 Face ID가 열렸다가 바로 돌아오고, 웹뷰는 없습니다. 백엔드는 그 증명을 직접 검증한 뒤 자체 토큰을 발급합니다.

**약 3주 반 동안 14개 태스크**를 진행했습니다. 가입, 로그인, 로그인 수단 연결·해제, 이메일 인증번호, 그리고 소셜 전용 사용자에게도 쓸모 있어진 아이디 찾기까지 다뤘습니다. 유닛 테스트는 536개에서 **880개**로 늘었고, 전체 여정을 실제 HTTP로 걷는 e2e 스위트가 새로 생겼습니다.

## 아키텍처 결정

### 1. 브로커 없이: 백엔드가 제공자를 직접 검증한다

**목표:** 앱 투 앱 로그인(웹뷰 없이)을 만들고, 어떤 벤더에 무슨 일이 생겨도 계정은 온전히 내 것으로 남기는 것.

**선택지:**
- **Firebase Auth나 Supabase Auth**를 브로커로 둔다. 앱은 브로커에 로그인하고, 서버는 브로커의 토큰을 믿는다.
- 시스템 브라우저를 거치는 **웹 OAuth 리다이렉트 흐름**.
- **앱은 네이티브 SDK, 검증은 내 서버:** 앱이 제공자의 증명을 보내면 백엔드가 확인하고 자체 JWT를 발급한다.

**결정:** 네이티브 SDK + 직접 검증.

**이유:**
- **앱 투 앱 로그인에는 어차피 제공자별 네이티브 SDK가 필요합니다.** 브로커를 써도 SDK는 그대로 필요하니, 경유지만 하나 더 생길 뿐입니다.
- **브로커를 쓰면 모든 사용자가 브로커의 ID에 묶입니다.** 나중에 떠나려면 모든 계정을 다시 매핑해야 합니다.
- **제공자들은 이미 표준(OpenID Connect)을 따릅니다.** 그래서 "직접 검증"은 프로젝트급 작업이 아니라 코드 수백 줄이었습니다.

**결과:** 소셜 로그인도 비밀번호 로그인과 똑같은 곳에서 끝납니다. `AuthService.issueSessionFor(userId)`가 발급하는 우리 액세스·리프레시 토큰입니다. 중간에 끼는 제3의 서비스는 없습니다.

### 2. 인터페이스 하나, 검증기 넷, 그리고 테스트용 가짜

**목표:** 네 제공자가 네 가지 방식으로 신원을 증명하는데, 앱의 나머지 부분은 지금 어떤 제공자와 대화 중인지 몰라도 되게 하는 것.

**선택지:** 필요한 곳마다 `switch (provider)`를 쓰거나, **어댑터 패턴**으로 하나의 모양에 제공자별 클래스를 하나씩 둔다.

**결정:** 인터페이스 하나를 네 번 구현합니다.
```ts
export interface SocialIdentityVerifier {
  verify(credential: Record<string, unknown>, nonce?: string): Promise<SocialIdentity>;
  disconnect(login: { providerUserId: string; refreshToken: string | null }): Promise<void>;
}
```
`SocialIdentity`가 공통 언어입니다: `{ provider, providerUserId, email, emailVerified, name, refreshToken }`.

**이유:** 제공자마다의 특이점은 각자의 파일 안에만 머뭅니다.
- **카카오 ID 토큰에는 `email_verified` 클레임이 없어서,** 대신 카카오 어드민 API에 물어봅니다.
- **애플에는 고정된 클라이언트 시크릿이 없습니다.** 호출할 때마다 `.p8` 키로 ES256 JWT를 새로 서명합니다.
- **안드로이드의 페이스북은 내용을 알 수 없는 액세스 토큰을 보냅니다.** 그래서 페이스북에 직접 확인해야 합니다(`debug_token`이 *우리* 앱의 토큰이라고 답해야 합니다).
- **구글은 리프레시 토큰을 최초 동의 때만 줍니다.**

**결과:** 주입 토큰 하나가 `Record<SocialProvider, SocialIdentityVerifier>`를 들고 있고, 시작 시 `SOCIAL_VERIFIER=real|fake`에 따라 한 번 만들어집니다. `Record`라서 제공자 하나를 빠뜨린 맵은 컴파일러가 거부합니다. 테스트에서는 `FakeSocialVerifier`가 제공자별로 따로 동작하므로, "카카오" 토큰을 구글 경로로 보내면 진짜처럼 실패합니다.

### 3. `jose`로 서명을 오프라인 검증하고, 누구의 실패인지 구분한다

**목표:** "카카오가 말하길, 이 사람은 사용자 4012345678이고 **Inventra에** 로그인하는 중"이라는 사실을 빠르게, 요청을 믿지 않고 증명하는 것.

**선택지:** 토큰마다 제공자에게 유효한지 물어본다. 제공자별 서버 SDK를 쓴다. 또는 제공자가 공개한 공개키 목록(JWKS)으로 토큰의 **서명**을 로컬에서 검증한다.

**결정:** 캐시되는 `createRemoteJWKSet`에 대해 `jose`의 `jwtVerify`로 검증하고, 서버 간 호출이 꼭 필요한 몇 군데만 순수 REST + `fetch`를 씁니다. 네 제공자 모두 이 방식입니다. 애초에 이 용도의 공식 Node SDK가 있는 곳은 구글뿐입니다.

**이유:**
- **서명 검증은 네트워크 호출이 아니라 수학입니다.** 키는 캐시되므로, 대부분의 로그인은 제공자를 전혀 호출하지 않습니다.
- **검증 항목은 어디서나 같습니다:** RS256만 허용, 발급자, **대상**(*다른* 앱에 발급된 토큰으로 여기 로그인하면 안 됩니다), 만료.
- **제공자 넷에 패턴 하나**가, 그중 하나에만 쓰는 SDK보다 낫습니다.

**결과:** 공용 `verifyIdToken` 하나가 실패가 **누구 탓인지**까지 판정합니다.
- 잘못된 토큰 → **401**. 앱은 로그인을 처음부터 다시 합니다.
- 제공자의 키 서버에 닿지 못함 → **503**. 앱은 재시도합니다.

카카오 이메일 조회나 구글·애플의 리프레시 토큰 교환 같은 부가 작업은 **실패해도 막지 않습니다**. 로그인은 그대로 되고, 부가 값만 `null`이나 "미인증"이 됩니다.

### 4. 논스: 토큰 하나는 로그인 한 번에만 쓸 수 있다

**목표:** 유출된 ID 토큰(카카오는 모바일에서 12시간 유효합니다)으로 남이 로그인할 수 없게 하는 것.

**결정:**
1. 앱이 `POST /auth/social/nonce`에서 무작위 **논스**를 받아, 그 **SHA-256 해시**를 제공자 SDK에 넘깁니다.
2. 제공자가 그 해시를 서명된 토큰 안에 봉인합니다.
3. 앱은 토큰과 **원본 논스**를 함께 우리에게 보냅니다.
4. 우리는 논스를 **소진**한 뒤(1회용, 5분), 토큰의 클레임이 그 논스의 SHA-256인지 확인합니다.

**이유:**
- **논스를 소진하면 재전송이 막힙니다.** 같은 논스는 두 번 통하지 않습니다.
- **클레임을 맞춰 보면 바꿔치기가 막힙니다.** 예전 토큰을 새 논스와 짝지을 수 없습니다.
- **토큰 안에는 해시만 들어 있으므로,** 토큰이 유출돼도 우리가 요구하는 원본 값은 드러나지 않습니다.

**결과:** 훔친 토큰은 쓸모가 없습니다. 재전송된 요청은 제공자에게 연락하기도 전에 거절됩니다.

### 5. 1회용 가입 티켓을 거치는 2단계 가입, 그리고 이메일로는 절대 매칭하지 않는다

**목표:** 처음 온 소셜 사용자도 나머지 가입 절차(인증된 전화번호, 회사 또는 가입 코드)를 거쳐야 하는데, 그건 *나중* 요청에서 일어납니다.

**선택지:**
- 가입할 때 제공자 증명을 다시 보낸다.
- 로그인 시점에 반쯤 완성된 계정을 만든다.
- **가입 티켓**을 돌려준다.

**결정:** 처음 보는 신원에는 `SIGNUP_REQUIRED`와 15분짜리 **가입 티켓**을 줍니다. 무작위 토큰이고, 그 SHA-256과 함께 "이 제공자가 이 사람을 증명했다"는 내용을 저장합니다. 가입은 **기존** 가입 엔드포인트로 하며, 태그가 붙은 `credentials` 객체(`{ type: 'password', … }` 또는 `{ type: 'social', signupToken, … }`)를 class-transformer 판별자로 검증합니다.

**이유:**
- **티켓이 요청과 요청 사이로 증명을 안전하게 옮깁니다.** 전화 인증 토큰과 같은 "한 번만 쓴다" 패턴입니다.
- **이메일로 계정을 연결하지 않습니다.** 어떤 구글 계정이 마침 기존 사용자와 같은 이메일을 쓴다고 그 계정으로 로그인시키면 **계정 탈취**입니다. 처음 보는 신원은 언제나 가입으로 갑니다.

**결과:** 역할별 가입 엔드포인트는 하나, 자격 증명 종류는 둘입니다. 전화 토큰, 티켓, (필요하면) 이메일 증명을 **한 트랜잭션** 안에서 함께 소진합니다. 어디서든 실패하면 모든 증명이 소진되지 않은 채로 남으므로, 그냥 다시 시도하면 됩니다.

### 6. 연락처 이메일은 인증번호로 증명하고, 번호를 가린 채 큐로 보낸다

**목표:** 알림을 받을 실제 메일함이 필요한데, 애플(첫 로그인 이후)과 일부 카카오 사용자는 인증된 이메일을 주지 않습니다.

**결정:** 제공자의 인증된 이메일, **또는** 사용자가 입력하고 6자리 인증번호로 증명한 주소(`POST /auth/email/start` / `confirm`), **아니면** 400입니다. 인증번호는 HMAC으로 저장하고, 60초 쿨다운(앱이 카운트다운을 보여주도록 `retryAfterSeconds` 포함), 하루 10회, 시도 5회 제한을 둡니다.

**이유:** 모든 알림을 큐로 보내고 싶었지만, 큐에 들어가는 행은 본문을 저장합니다. 그러면 인증번호가 데이터베이스에 평문으로 남습니다. 그래서 행에는 `******`만 저장하고, 실제 본문은 BullMQ 잡 안에만 실어 보냅니다(잡은 완료 시에도 실패 시에도 삭제됩니다). 리컨실러는 이런 행을 다시 보내지 않고 실패로 기록합니다.

**결과:** e2e 스위트는 Mailpit에서 실제 인증번호를 읽은 뒤, `notifications` 행에는 `******`만 있고 번호는 절대 없다는 것을 확인합니다.

### 7. 경합 판정은 데이터베이스에게: 조건부 쓰기를 쓰고, 에러는 잡지 않는다

**목표:** 같은 카카오 신원이 같은 순간에 두 번 가입해도(티켓 두 장, 버튼 두 번 탭) 계정은 정확히 하나여야 합니다.

**선택지:**
- 먼저 확인하고 삽입한다(두 요청이 모두 확인을 통과할 수 있습니다).
- 삽입하고 Postgres의 유니크 위반 에러(Prisma `P2002`)를 **잡는다**.
- 중복을 개수로 알려 주는 **조건부 삽입**.

**결정:** 조건부 삽입입니다. `createMany({ skipDuplicates: true })`는 `INSERT … ON CONFLICT DO NOTHING`이 되고, `count === 0`이면 409입니다. 새 행이 필요한 곳에서는 `createManyAndReturn`이 대신 빈 배열을 돌려줍니다.

**이유:**
- **처음에는 에러를 잡는 버전을 썼고, 동작했습니다.** 하지만 올바른 `P2002`를 알아보려면 Prisma 7의 에러 객체를 파헤쳐야 했습니다. pg 어댑터에서는 컬럼 정보가 대부분의 가이드가 말하는 `meta.target`이 아니라 `meta.driverAdapterError.cause.constraint.fields`에 있습니다. 어느 릴리스에서든 바뀔 수 있는 모양입니다.
- **개수는 지루하지만 안정적입니다.** 게다가 이 코드베이스가 1회용 토큰에 이미 쓰던 패턴(`where`에 조건을 넣은 `updateMany`)과 같습니다.

**결과:** 이제 이것은 `CLAUDE.md`에 적힌 프로젝트 규칙입니다. **강제는 유니크 인덱스가, 판정 결과는 개수가 알려 준다.** 연결이 거절되면 *그 뒤에* 읽기를 한 번 해서 어떤 규칙에 걸렸는지만 설명합니다. 메시지는 정확하면서 경합의 틈은 다시 열리지 않습니다.

### 8. "마지막 로그인 수단은 지울 수 없다", 그리고 조건부 쓰기로는 못 잡는 경합

**목표:** 연결 해제 때문에 로그인할 방법이 하나도 없는 계정이 생겨서는 안 됩니다.

**문제:** 두 기기가 같은 순간에 마지막 **두** 로그인 수단을 해제하면, 둘 다 "2개"를 세고 둘 다 삭제합니다. 각 요청이 *서로 다른* 행을 지우므로 어떤 유니크 규칙에도 걸리지 않습니다(데이터베이스에서 "write skew"라고 부르는 현상입니다).

**결정:** 두 요청이 먼저 하나의 공유 행을 건드리게 합니다. 사용자 본인 행에 쓰기를 하면(`user.updateMany({ … updatedAt })`) 그 **행 잠금**을 잡게 되어, 두 번째 해제는 기다렸다가 **1개**를 세고 409를 받습니다.

**결과:** 실제 Postgres에서 동시 해제 두 건으로 확인했습니다. **잠금이 없으면 로그인 수단 0개, 있으면 409 한 건에 로그인 수단 1개가 남았습니다.** 제공자 연결 끊기(카카오 연결 해제, 구글·애플 토큰 철회, 페이스북 권한 회수)는 커밋 후에 최선을 다하는 방식으로 실행되므로, 제공자 장애가 잠금을 붙잡거나 해제를 되돌릴 수 없습니다.

### 9. 소문자 이메일, *부분* 유니크 인덱스, 그리고 구조해야 했던 마이그레이션

**목표:** `Jane@Acme.com`과 `jane@acme.com`은 같은 메일함이고, 비밀번호 로그인 이메일 하나는 계정 하나에만 속하게 하는 것.

**결정:**
- **이메일은 들어오는 문 앞에서 소문자로 만듭니다.** 모든 DTO, 제공자 이메일, 시드가 같은 `normalizeEmail`을 씁니다. 이미 저장된 행은 데이터 마이그레이션으로 고쳤고, 이 마이그레이션은 비밀번호 로그인 둘이 같은 이메일이 되는 경우엔 실행을 거부합니다.
- **비밀번호 로그인 이메일 하나에 계정 하나를 데이터베이스가 강제합니다.** *부분* 유니크 인덱스 `UNIQUE (email) WHERE method = 'local'`입니다. 제공자 행끼리는 이메일이 같아도 되지만, 비밀번호 행끼리는 안 됩니다.

**두 번 잘못된 일:**
1. **사용자가 이미 적용한 마이그레이션을 제가 수정했습니다.** `migrate dev`가 "divergence"를 보고하며 *데이터베이스 초기화*를 제안했습니다. 파일을 `_prisma_migrations`의 체크섬과 일치하도록 바이트 단위로 복원하고, 변경 사항은 새 마이그레이션으로 옮겼습니다. 배운 규칙: 적용된 마이그레이션은 절대 수정하지 않는다.
2. **Prisma가 인덱스를 계속 "고치려" 했습니다.** Postgres는 조건을 `((method)::text = 'local'::text)`로 저장하는데, Prisma는 그 텍스트를 자신의 `("method" = 'local')`과 비교해 다르다고 판단하고, `migrate dev` 때마다 DROP + 똑같은 CREATE를 만들었습니다. 그 쓸모없는 마이그레이션의 UTC 타임스탬프가 진짜보다 **앞에** 정렬되는 바람에, 새 데이터베이스는 "index does not exist"로 실패했습니다. 해결책은 조건을 Postgres가 저장하는 그대로 `where: raw("((method)::text = 'local'::text)")`로 적고, `migrate diff`가 "empty migration"을 내는지 확인하는 것이었습니다.

**결과:** 비밀번호 가입과 "비밀번호 추가"도 이제 다른 곳과 같은 조건부 삽입으로 이 인덱스에 기댑니다.

## TIL (오늘 배운 것)

**"앱 X는 우리 앱인가요, 제공자인가요?"**
우리 앱입니다. OAuth 용어로 Inventra는 **클라이언트**, 사용자는 **리소스 소유자**이고, 제공자는 **인가 서버**와 **리소스 서버**를 운영합니다. `aud` 검사에서 "다른 앱에 발급됐다"는 말은 등록된 *다른 클라이언트*를 뜻합니다.

**"실서비스에서 카카오 검증은 어떻게 동작하나요? 어드민 키로 사용자를 검증하는 줄 알았어요."**
어드민 키는 아무것도 검증하지 않습니다. 이 키는 우리 사용자 *누구든* ID만으로 조회할 수 있으니, 지금 휴대폰을 들고 있는 사람이 누구인지는 증명하지 못합니다. 증명은 ID 토큰의 **서명**이고, 카카오의 공개키로 로컬에서 확인합니다. 어드민 키는 신원이 증명된 *뒤에*, 그 사용자의 이메일이 인증됐는지 물을 때만 등장합니다.

**"정확히 뭘 캐시하고, 왜 하나요?"**
제공자의 **공개키 목록**(JWKS)뿐입니다. 토큰이나 사용자는 캐시하지 않습니다. `jose`는 10분이 지나면 목록을 새로 받고, 토큰이 모르는 키를 가리키면 더 일찍 다시 받습니다. 키 교체는 이렇게 처리됩니다. 30초 쿨다운도 있어서, 꾸며낸 키 ID로 카카오를 마구 호출하게 만들 수도 없습니다.

**"논스 해시에는 왜 솔트가 없나요? 그리고 솔트를 친 비밀번호는 대체 어떻게 검증하나요?"**
솔트는 *추측할 수 있는* 입력을 미리 계산된 표로부터 지킵니다. 32바이트 무작위 논스는 추측할 수 없고, 그 해시는 원본 값만으로 다시 만들 수 있어야 합니다. 행을 찾을 때도, 토큰의 클레임과 맞춰 볼 때도요. 비밀번호의 경우 argon2가 솔트를 해시 문자열 *안에* 저장하고, `verify`가 그걸 다시 씁니다. (암호화에는 솔트가 아예 없습니다. AES-GCM은 **IV**를 쓰고, IV는 같은 키로 절대 반복되면 안 됩니다.)

**"중복을 에러에 기대지 않고 처리하는 다른 방법이 있나요?"**
있습니다. `skipDuplicates`(`ON CONFLICT DO NOTHING`)는 중복을 `count: 0`으로 알려 줍니다. 먼저 확인하는 방식으로는 유니크 인덱스를 대신할 수 없습니다. 두 요청은 서로의 아직 커밋되지 않은 행을 볼 수 없고, 둘을 모두 보는 건 데이터베이스뿐이니까요.

**"'비밀번호 로그인 이메일'이 무슨 뜻이에요? 사용자는 로그인 수단이 여러 개잖아요."**
바로 그렇습니다. 테이블 하나에, 로그인 수단 하나당 행 하나입니다. `local` 행에서는 이메일이 곧 로그인 ID이고, 제공자 행에서는 그저 참고 정보입니다. 그래서 유니크 규칙을 부분 인덱스로 만들어야 했습니다.

**"`nonce`와 `:provider`가 같은 경로 레벨에 있는 게 마음에 들지 않아요."**
타당한 지적입니다. `/auth/social/:provider`가 먼저 선언되면 `/auth/social/nonce`에도 매칭됩니다. 제공자를 본문으로 옮기자(`POST /auth/social/login { provider, … }`) 이런 종류의 문제가 통째로 사라졌습니다.

**"이걸 제공자 SDK로 할 수 있나요, 아니면 REST뿐인가요?"**
서버 쪽 공식 Node 라이브러리가 있는 건 구글(`google-auth-library`)뿐입니다. 카카오, 애플, 페이스북은 서버 쪽을 **REST API로** 문서화합니다. 네 곳 모두 REST + `jose`로 통일해서, 읽고 테스트할 패턴을 하나로 유지했습니다.

**"소셜 로그인의 경합은 어떻게 막았나요?"**
두 조각입니다. 데이터베이스 규칙(유니크 인덱스 `(method, provider_user_id)`)과, "이미 있으면 말고"라고 묻는 삽입입니다. 두 번째 요청은 첫 번째가 커밋할 때까지 인덱스에서 **기다렸다가**, 아무것도 넣지 않습니다. 먼저 확인하는 방식에 있던 틈은 아예 없습니다.

**"`isRedacted`는 `JobsOptions`에 없는 필드인데, 어떻게 거기서 쓰이죠?"**
BullMQ에 전달되는 게 아닙니다. `...(isRedacted ? A : B)`는 호출 전에 *우리* 코드가 계산하고, 고른 객체의 속성만 펼쳐 넣습니다. `isRedacted`라는 키를 넣었다면 타입 검사에서 걸렸을 겁니다. 이 식은 고르기만 합니다.

## NestJS 개념과 라이브러리

| 개념 / 라이브러리 | 사용한 이유 |
|---|---|
| `jose` (`jwtVerify`, `createRemoteJWKSet`, `SignJWT`, `importPKCS8`, 타입이 있는 `errors`) | ID 토큰 오프라인 검증, 애플 클라이언트 시크릿 서명, 401과 503 구분 |
| OpenID Connect + OAuth 2.0 | 네 제공자가 모두 따르는 표준 (ID 토큰, 인가 코드, 철회) |
| 주입 토큰 + `useFactory` + `Record<SocialProvider, Verifier>` | 환경별 실제/가짜 검증기, 빠짐없는 맵 |
| class-transformer 판별자 (`subTypes`가 있는 `@Type`) | `credentials` 필드 하나에 검증되는 두 가지 모양 |
| `@Transform(normalizeEmail)` | 검증 전에 모든 이메일을 소문자로 |
| `node:crypto` (`randomBytes`, SHA-256, HMAC, `timingSafeEqual`, AES-256-GCM) | 논스, 티켓, 인증번호 해시, 암호화된 리프레시 토큰 |
| Prisma `createMany` / `createManyAndReturn` `{ skipDuplicates }` | 개수로 알려 주는, 경합에 안전한 삽입 |
| Prisma 대화형 트랜잭션 + `Prisma.TransactionClient` | 전화 토큰·티켓·이메일 증명을 함께 소진하거나, 아예 소진하지 않거나 |
| Prisma 부분 인덱스 (프리뷰)와 `raw()` | 끝없는 drift 없이, 비밀번호 로그인 이메일 하나에 계정 하나 |
| Prisma 중첩 `select`와 `orderBy` | 아이디 찾기가 사용자와 모든 로그인 수단을 쿼리 한 번에 읽음 |
| BullMQ 잡 데이터 + `removeOnFail` | 알림 테이블에 저장하지 않고 인증번호 보내기 |
| `Test.createTestingModule().overrideModule()` | Redis만 빼고 실제 모듈 그래프를 만드는 연결 테스트 |
| e2e에서 Mailpit HTTP API | 실제로 발송된 인증번호를 읽고, 앱 밖으로 나간 것을 검증 |
| `ParseUUIDPipe` | 형식이 잘못된 로그인 수단 ID는 DB 에러가 아니라 400 |

## 마무리

이번 트랙에서 만든 것:
- **카카오·구글·페이스북·애플 로그인과 가입**, 백엔드가 직접 검증
- **논스와 1회용 가입 티켓**, 유출된 토큰은 쓸모없게
- **인증번호로 증명하는 연락처 이메일**, 번호는 한 번도 저장하지 않고 큐로 발송
- **로그인 수단 관리**: 제공자 연결, 비밀번호 추가, 연결 해제(마지막 하나는 불가)
- **소문자 이메일**과 데이터베이스가 강제하는 **비밀번호 로그인 이메일당 계정 하나**
- 막다른 길 대신 **"카카오로 가입하셨어요"라고 답하는 아이디 찾기**
- 하나의 신원을 두고 경합하는 두 가입까지 포함해, 전체 여정을 걷는 **e2e 스위트**

간직할 교훈은 이것입니다. 두 요청이 충돌할 수 있는 곳이라면 판정은 데이터베이스가 해야 합니다. 제 코드는 데이터베이스에 질문을 하고(조건부 삽입, 행 잠금) 단순한 답을 읽으면 됩니다. 에러 메시지를 해석할 일이 아닙니다.

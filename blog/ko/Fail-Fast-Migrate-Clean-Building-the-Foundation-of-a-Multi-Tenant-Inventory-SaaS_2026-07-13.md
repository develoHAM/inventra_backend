# 빠르게 실패하고, 깔끔하게 마이그레이션하기: 멀티테넌트 재고관리 SaaS의 기반 다지기

*Inventra 프로젝트의 Phase 0 — 이후의 모든 것이 올라설 인프라, 설정, 데이터베이스 토대에 관한 이야기.*

**2026-07-13**

---

저는 한국의 편집숍/입점 매장 모델을 바탕으로 한 멀티테넌트 재고관리 SaaS **Inventra**를 만들고 있습니다. 여러 회사와 브랜드가 물리적 매장(예: 교보문고 강남점) 안에서 각자의 "코너"를 운영하며 각자의 재고를 관리하는 구조입니다. 스택은 **NestJS, Prisma, PostgreSQL**이고 Redis는 이후 단계에서 도입할 예정입니다.

기능을 한 줄 짜기 전에, 저는 **재현 가능하고(reproducible), 빠르게 실패하며(fail-fast), 타입 안전한(type-safe)** 기반을 먼저 만들고 싶었습니다. 이 글은 Phase 0 — Docker, 검증된 설정, 데이터베이스 — 를 구성하며 내린 결정들과, 그 과정에서 겪은 실수들에 대한 기록입니다.

## 아키텍처 결정

### 1. Postgres + Redis를 위한 Docker Compose

- **목표:** 내 컴퓨터에서도, 다른 누구의 컴퓨터에서도 똑같이 동작하는 DB와 캐시. "제 컴퓨터에서는 되는데요"를 없애기.
- **선택지:** macOS에 Postgres/Redis를 네이티브로 설치하거나, Docker Compose로 컨테이너로 실행하거나.
- **선택:** Docker Compose.
- **이유:** `docker-compose.yml` 하나가 정확한 버전, 포트, 볼륨, 헬스체크를 기술합니다. `docker compose up -d` 한 줄로 전체 환경이 재현되고, named volume 덕분에 재시작해도 데이터가 유지됩니다.
- **결과:** 커밋해서 공유 가능한 환경. 동료가 레포를 클론하면 몇 초 만에 동일한 Postgres 17 + Redis 8을 얻습니다.

### 2. 환경변수 검증에 Joi가 아닌 Zod

- **목표:** 필수 환경변수가 없거나 잘못됐다면 앱이 부팅을 거부해야 한다 — 새벽 2시의 엉뚱한 코드 경로가 아니라, **시작 시점에 큰 소리로**.
- **선택지:** Joi(`@nestjs/config` 문서의 기본값) 또는 Zod.
- **선택:** Zod. `ConfigModule.forRoot`의 범용 `validate` 함수에 연결.
- **이유:** Zod는 TypeScript 우선 설계라, 스키마 하나로 **런타임 검증**과 **정적 타입**(`z.infer`)을 동시에 얻습니다. Joi를 쓰면 런타임 검증과 별개로 설정 타입을 손으로 다시 써야 하고, 둘은 결국 어긋납니다. Zod는 한 소스에서 둘을 동기화합니다.
- **결과:** `config.get('PORT', { infer: true })`가 진짜 `number`를 반환하고, `DATABASE_URL`이 없으면 읽기 쉬운 에러와 함께 부팅이 중단됩니다. 빠르게 실패하고, 타입 안전한 설정.

### 3. 진실의 원천(source of truth)으로서의 Prisma 스키마 — 인트로스펙션이 아니라 직접 작성

- **목표:** DB 스키마를 한 곳에서 소유하고, 버전 관리되는 마이그레이션으로 진화시키기.
- **선택지:** 기존 SQL DDL을 Prisma로 인트로스펙션하거나, `schema.prisma`를 직접 작성하고 Prisma가 마이그레이션을 생성하게 하거나.
- **선택:** 직접 작성.
- **이유:** 앞으로 Prisma를 유일한 진실의 원천으로 삼고, 지저분한 인트로스펙션 베이스라인이 아닌 깔끔한 마이그레이션 히스토리를 원했습니다.
- **결과:** 도메인별로 나뉜 파일에 19개 모델. 핵심은 **테넌트 격리를 강제하는 복합 외래키(composite FK)** 입니다. 주문 항목의 상품과 그 부모 주문이 `company_store_id` 컬럼을 두 FK에 걸쳐 공유하기 때문에, DB 차원에서 서로 다른 코너를 섞는 것이 *구조적으로 불가능*해집니다. Prisma가 표현하지 못하는 것들(`CHECK` 제약, 식별 컬럼에 대한 취향)은 `--create-only`로 마이그레이션을 생성한 뒤 SQL을 직접 수정해 적용했습니다.

### 4. Prisma 7의 드라이버 어댑터를 NestJS DI로 연결

- **목표:** 하나의 공유되고 생명주기가 관리되는 DB 연결.
- **선택지:** 필요할 때마다 `new PrismaClient()`를 만들거나, 주입 가능한 `PrismaService` 하나를 쓰거나.
- **선택:** `PrismaClient`를 상속한 `PrismaService`를 전역으로 제공.
- **이유:** 하나의 커넥션 풀, connect/disconnect를 관리하는 한 곳, 그리고 테스트에서 목(mock)할 수 있는 접점. Prisma 7은 이제 드라이버 어댑터를 *필수*로 요구하므로, 이 서비스는 검증된 `DATABASE_URL`로 `PrismaPg` 어댑터를 만들어 `super()`에 넘깁니다.
- **결과:** 어떤 서비스든 `PrismaService`를 주입해 `this.user.findMany()`를 바로 호출하고, 부팅 시 연결되고 종료 시 해제되는 단일 풀이 뒷받침합니다.

## 오늘 배운 것 (TIL)

**Q: Docker Desktop을 종료했더니 왜 모든 `docker` 명령이 깨졌나요?**
macOS의 Docker는 리눅스 VM 안에서 백그라운드 **데몬**(`dockerd`)을 돌리고, 실제로 컨테이너를 실행하는 건 그 데몬이기 때문입니다. `docker` CLI는 데몬에 요청을 보내는 클라이언트일 뿐입니다. Docker Desktop을 끄면 데몬이 죽어서 CLI가 말을 걸 상대가 사라집니다. 전원이 뽑힌 TV의 리모컨인 셈이죠.

**Q: Dockerfile과 docker-compose의 차이는?**
**Dockerfile**은 이미지 *하나*를 빌드하는 레시피이고, **docker-compose**는 *여러* 컨테이너를 함께 오케스트레이션합니다(제 경우 미리 빌드된 Postgres/Redis 이미지를 실행하므로 Dockerfile이 필요 없습니다). Dockerfile은 상자를 만들고, Compose는 상자들의 묶음을 실행합니다.

**Q: 빌드가 "Found 0 errors"라고 해놓고 "Cannot find module dist/main"으로 죽었어요. 왜죠?**
오래된 TypeScript 증분(incremental) 캐시 때문입니다. `deleteOutDir`가 `dist/`를 지웠는데, 프로젝트 루트에 있던 `.tsbuildinfo` 캐시는 여전히 "다 컴파일됨"이라고 우겨서 tsc가 아무것도 출력하지 않은 겁니다. 해결책: `tsBuildInfoFile`로 캐시를 `dist` **안으로** 옮겨, `dist`를 지우면 캐시도 함께 지워지게 해 둘이 어긋나지 않도록 했습니다.

**Q: `id`가 이미 유일한데 왜 `company_store_products`에 `@@unique([id, companyStoreId])`가 필요한가요?**
외래키는 **유니크 제약**만 참조할 수 있는데, 자식 테이블이 `id` 하나가 아니라 `(id, company_store_id)` *쌍*을 참조해야 하기 때문입니다. 그 "중복처럼 보이는" 유니크는 순전히 합법적인 FK 대상이 되기 위해 존재하고, 그것이 바로 상품과 주문이 같은 코너에 속함을 DB가 보장하게 해 줍니다.

**Q: `sslmode=require`가 TLS 에러로 로컬 연결을 깼어요. 왜?**
그 파라미터는 암호화 연결을 강제하는데, 로컬 Postgres 컨테이너는 TLS를 제공하지 않습니다. `sslmode=require`는 *프로덕션*(관리형 DB는 이를 요구함)에서 쓰는 것이고, 로컬에서는 제거했습니다. "프로덕션 설정을 로컬에 그대로 쓰지 말 것"의 교과서적 사례였습니다.

**Q: Prisma 7은 왜 "adapter" 없이는 연결을 거부하나요?**
Prisma 7은 번들된 쿼리 엔진을 버리고 **드라이버 어댑터** 방식으로 바뀌었습니다 — 쿼리 로직은 JS로 돌리고, 실제 연결은 표준 드라이버(`PrismaPg`를 통한 `pg`)에 위임합니다. 그래서 클라이언트가 더 이상 `DATABASE_URL`을 마법처럼 읽지 않고, 어댑터를 직접 만들어 넘겨줘야 합니다. 더 명시적이지만, 직접 연결해 줘야 합니다.

## 사용한 NestJS 개념과 라이브러리

| 항목 | 이유 |
|---|---|
| `@nestjs/config` + `ConfigService` | 검증된 설정을 DI로 로드하고 노출. |
| **의존성 주입(DI)** | 클래스가 생성자에서 필요한 것을 선언하면 Nest가 공유 싱글턴을 공급 — 테스트 가능하고 결합도 낮음. |
| **모듈** (`@Module`, `@Global`) | 프로바이더를 묶고 공유. `PrismaModule`은 전역이라 모든 기능이 DB를 주입 가능. |
| **생명주기 훅** (`OnModuleInit`/`OnModuleDestroy`) | 시작 시 DB 연결, 정상 종료 시 연결 해제. |
| **Zod** | 스키마 하나로 환경변수의 런타임 검증 + 정적 타입. |
| **Prisma 7** + `@prisma/adapter-pg` | 타입 안전한 데이터 접근. pg 드라이버 어댑터가 연결을 제공. |

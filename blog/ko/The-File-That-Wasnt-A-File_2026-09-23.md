# 파일이 아니었던 파일 (The File That Wasn't a File)

> "발주에 파일을 첨부"하려던 기능이, 컬럼 순서가 곧 API인 스프레드시트 왕복 기능이 되었다.

*2026-09-23*

## 들어가며

[Inventra](https://github.com/develoHAM/inventra_backend)는 **NestJS 11 + Prisma 7 + PostgreSQL**로 만든 멀티테넌트 재고관리 SaaS로, 한국의 편집숍·매장 입점 모델을 본떴다. [지난 글](./Keys-That-Expire_2026-09-16.md)에서는 파일 업로드를 붙였다. 상품 이미지, 브랜드 로고, 아바타를 모두 비공개로 MinIO에 두고 presigned URL로 내려주는 구조였다. 할 일 목록의 마지막 항목은 "**발주 파일 + 실사 파일**"이었고, 나는 당연히 같은 방식이 반복될 거라고 생각했다.

아니었다. 발주 파일로 어떤 형식을 받을지 물었더니 돌아온 답은 *"발주 + 발주 상세 조회 결과와 똑같은 구조의 엑셀이나 CSV"*였다. 그러니 할 일은 문서를 보관하는 게 아니라 **데이터 교환**이었다. 발주·실사를 스프레드시트로 내보내고, 다시 가져오는 기능이다. 이번 글은 그 양쪽을 다룬다.

## 아키텍처 결정들

### 1. 관점 전환: 첨부 파일이 아니라 데이터 교환

**목표:** 사용자가 실제로 원하는 방식으로 발주·실사를 파일로 다루게 하기.

**선택지:**
- 업로드된 시트를 불투명한 첨부 파일로 저장한다. `fileUrl` 컬럼과 이미지에 쓰던 presign 방식을 그대로 쓴다.
- 시트를 **구조화된 데이터**로 다룬다. 내보낼 때는 DB에서 생성하고, 가져올 때는 레코드로 파싱한다.

**선택:** 구조화된 데이터, 양방향 모두.

**이유:** 저장만 된 첨부 파일은 막다른 길이다. 조회도, 검증도, 재고 이동으로 바꾸는 것도 안 된다. 사용자가 원한 건 열어서 고치고 다시 올릴 수 있는 스프레드시트였다. 즉 blob이 아니라 데이터 포맷이다.

**결과:** 이 기능은 `StorageService`도, presigned URL도, `fileUrl`도 전혀 건드리지 않는다. 컬럼 규약 하나를 공유하는 별도 서브시스템이 됐고, 이 방향 전체가 질문 하나에서 나왔다.

### 2. 행은 평평하게 두고, 헤더 값은 행마다 반복한다

**목표:** CSV와 xlsx 모두에서 똑같이 동작하고, 가져오기에서 확실하게 다시 읽을 수 있는 하나의 시트 레이아웃.

**선택지:**

| 레이아웃 | 중복 | CSV에서 동작 | 가져오기 복잡도 |
|---|---|---|---|
| **평평한 표:** 품목 1개당 1행, 발주 정보는 행마다 반복 | 있음 | 예 | 매우 단순 |
| **두 블록:** 위쪽에 발주 정보 한 번, 그 아래 품목 표 | 없음 | 어색함 | 파서 두 개 |
| **두 시트** (발주 + 품목) | 없음 | 아니오 (xlsx만) | 서로 다른 규약 두 개 |

**선택:** 평평한 표.

**이유:** 반복되는 발주 값을 없앨 수 없느냐고 물었고, 타당한 질문이었다. 하지만 CSV는 *원래* 사각형 표 하나이고, 이는 `order ⋈ items ⋈ product`를 조인한 쿼리 결과와 정확히 같은 모양이다. 반복 덕분에 각 행이 그 자체로 완결된다. 엑셀 필터, pandas, SQL `COPY` 모두 한 번에 읽을 수 있고, 두 형식에서 똑같은 유일한 레이아웃이기도 하다.

**결과:** 내보내기, 가져오기, CSV, xlsx가 모두 하나의 컬럼 규약을 공유한다.

### 3. 워크북 하나, 직렬화 두 가지: exceljs, 기본은 CSV

**목표:** 생성기를 두 번 만들지 않고 두 형식을 모두 만들기.

**선택:** **exceljs** 위에 공유 `@Global() SpreadsheetService`를 둔다. 표는 한 번만 정의하고, 필요한 직렬화 함수를 호출한다.

```ts
worksheet.columns = columns;   // [{ header, key }]
worksheet.addRows(rows);       // `key`로 값을 찾는 객체들
format === 'csv' ? await workbook.csv.writeBuffer()
                 : await workbook.xlsx.writeBuffer();
```

**이유:** 정의 하나, 의존성 하나로 끝나고, 출력 형식은 마지막 호출만 바꾸면 된다. 어디서나 열리는 **CSV를 기본값**으로 했고, xlsx는 `?format=xlsx`로 선택한다.

**결과:** 내보내기는 `GET …/export?format=csv|xlsx`이고, 컨트롤러가 버퍼를 `StreamableFile`로 스트리밍한다.

### 4. 헤더는 번역하고, key는 규약으로 남긴다

**목표:** **영어와 한국어**로 읽기 좋은 헤더.

**핵심 깨달음:** exceljs 컬럼에는 하는 일이 전혀 다른 두 필드가 있다. `header`는 1행에 쓰이는 텍스트이고, `key`는 exceljs가 행 객체에서 각 셀의 값을 찾는 이름이다. 그래서 둘을 떼어냈다.

```ts
{ key: 'productOrderQuantity', label: { en: 'Order Quantity', ko: '주문 수량' } }
// 내보낼 때: header = label[lang], key는 절대 바뀌지 않는다
```

**트레이드오프:** 헤더를 번역하는 순간, 가져오기는 헤더 텍스트로 컬럼을 맞출 수 *없다*. `주문 수량`은 `productOrderQuantity`가 아니니까. 그래서 가져오기는 **컬럼 위치**로 읽고, 그 위치는 내보내기가 쓰는 *바로 그* 컬럼 배열에서 찾는다.

**결과:** 한국어 시트와 영어 시트가 똑같이 가져와진다. 내보내기와 가져오기가 컬럼 순서 정의 하나를 공유하므로 서로 어긋날 수 없다.

### 5. 가져오기는 모든 오류를 모으고, 전부 정상일 때만 저장한다

**목표:** 200행짜리 스프레드시트 업로드를 두렵지 않은 작업으로 만들기.

**선택지:** 첫 번째 잘못된 행에서 멈추거나, 모든 행을 검사해 문제를 한꺼번에 알려주거나.

**선택:** 전부 검사한다. 모든 행을 검증하고(등록된 바코드인지, 이 코너에 진열된 상품인지, 수량이 최소값 이상의 정수인지, 바코드 중복은 없는지), 실패마다 `{ row, error }`를 만든다. row는 사용자가 스프레드시트에서 **실제로 보는 줄 번호**다.

```json
{ "message": "Import failed",
  "errors": [ { "row": 2, "error": "Quantity must be an integer ≥ 1" },
              { "row": 3, "error": "Unknown barcode \"ZZZ-999\"" } ] }
```

**이유:** 첫 오류에서 멈추면, 실수가 다섯 개인 사용자는 업로드를 다섯 번 해야 한다. 전체 목록을 주면 한 번에 모두 고칠 수 있다. 바코드는 행마다 쿼리하지 않고 **묶음 쿼리 두 번**으로 조회한다.

**결과:** 업로드 전체가 함께 성공하거나 함께 실패하고, 바로 조치할 수 있는 오류 목록이 돌아간다.

### 6. 가져오기는 기존 쓰기 경로를 재사용한다

**목표:** 검증되지 않은 두 번째 발주 생성 경로를 만들지 않기.

**선택:** 가져오기는 *번역기*일 뿐이다. `buildOrderDtoFromFile`은 바이트를 `POST /orders`가 이미 받는 것과 똑같은 `CreateOrderDto`로 바꾸고, 기존 `create` / `update`를 호출한다.

**결과:** 쓰기 로직이 중복되지 않는다. 같은 `$transaction`, 같은 진열 검사, 같은 복합키 처리를 탄다. 덕분에 규칙 하나도 공짜로 따라왔다. **이미 적용된 실사 위에 가져오기를 하면 409**가 나는데, 기존 `update`가 이미 그걸 거부하기 때문이다.

## TIL (오늘 배운 것)

### `header`와 `key`는 실제 파일과 어떻게 연결될까?
**파일에 나타나는 것**은 `header`뿐이다. 1행이다. `key`는 어디에도 쓰이지 않는다. exceljs가 각 셀을 채울 때 `row[key]`를 찾는 데만 쓴다. 첫 초안에서는 둘이 같아서, 서로 다른 일을 한다는 사실이 가려져 있었다. 읽기 좋은(그리고 번역된) 헤더를 원하는 순간, 둘을 떼어내는 것이 설계의 전부였다.

### 도대체 `StreamableFile`이 뭘까?
컨트롤러는 보통 객체를 반환하고, NestJS는 그걸 **JSON으로 인코딩**한다. 스프레드시트는 브라우저가 파싱할 게 아니라 *저장*해야 하는 원시 바이트다. `StreamableFile`은 그런 경우를 위한 Nest의 래퍼다. `new StreamableFile(buffer, { type, disposition })`을 반환하면 Nest가 `Content-Type`과 `Content-Disposition: attachment; filename="…"`을 설정하고 바이트를 흘려보낸다. 대안인 `@Res()`를 주입해 직접 응답에 쓰는 방식은 Nest의 응답 처리에서 빠져버린다.

### 모든 행의 제목과 날짜가 같다는 걸 어떻게 보장하지?
보장하지 못하고 있었고, 이건 내가 찾아낸 문제다. 첫 초안은 발주의 제목·설명·날짜를 첫 데이터 행에서 읽고, 나머지 행의 같은 셀은 **조용히 무시**했다. 누가 5행에 다른 제목을 적으면 그냥 사라지는 것이다. 해결책은 "모두 모은다"는 같은 원칙을 따른다. 뒤따르는 모든 행의 발주 정보는 첫 행과 **일치해야** 하고, 다르면 그 행이 오류가 된다. 평평한 레이아웃은 이 값들을 반복하므로, 이제 그 반복은 가정이 아니라 **검사 대상**이다. 서로 다른 발주 두 개라면 파일도 두 개다.

### 컨트롤러 메서드 순서가 중요할까?
경우에 따라 그렇다. **Express** 위의 NestJS는 선언된 순서대로 라우트를 등록하고, Express는 **먼저 맞는 것**을 쓴다. 고정 경로를 파라미터보다 우선하지도 않는다. 그래서 `@Post(':orderId')`가 `@Post('import')`보다 먼저 나오면, `/orders/import` 요청이 `orderId = "import"`로 잡힌다. 내 컨트롤러에는 `POST /orders/:orderId`가 없어서(수정은 `PATCH`다) 충돌은 없었다. 그래도 **같은 메서드·같은 경로 깊이에서는 고정 경로를 파라미터 경로보다 먼저 선언**하는 습관은 지킬 만하다. (Fastify는 이걸 알아서 정리해 주지만 Express는 아니다.)

### 실사는 가용·예약·샘플 재고를 어떻게 구분할까?
구분하지 않는다. 의도된 설계다. 실사 한 줄에는 센 숫자 **하나**만 있고, 실사를 적용하면 `ADJUSTMENT`, 즉 `{ kind: 'set', field: availableQuantity }`가 실행된다. 실사는 진열대 위의 판매 가능 재고만 맞춘다. 예약·샘플·파손 수량은 각자의 거래 유형으로만 바뀐다. 그래서 내보내기에 상품당 수량이 하나인 게 맞다.

### 사라지지 않던 오류: exceljs와 `Buffer`
`workbook.xlsx.load(buffer)`가 *"`Buffer<ArrayBufferLike>`는 `Buffer`에 할당할 수 없다"*며 타입 검사에서 실패했다. 첫 해결책인 `Buffer.from(buffer)`는 오류를 뒤집기만 하고 없애지 못했다. 진짜 원인은 **모든 Node `Buffer`는 `Uint8Array`**인데, exceljs의 오래된 타입 정의가 파라미터를 `ArrayBuffer` 모양으로 기술하고 있다는 점이다. 어떤 종류의 Node Buffer도 절대 그걸 만족할 수 없다. **두 라이브러리의 타입 정의가 어긋난 것일 뿐, 런타임에는 영향이 없다.** exceljs는 Buffer를 잘 읽는다. 그래서 그 호출 지점 한 줄의 캐스트, `buffer as unknown as ArrayBuffer`가 정직한 해결책이다. 교훈: 값을 바꿨는데 오류가 해결되지 않고 뒤집히기만 한다면, 값을 그만 만지고 두 타입이 애초에 호환될 수 있는지부터 봐야 한다.

## NestJS 개념 & 라이브러리

| 개념 / 라이브러리 | 왜 썼나 |
|---|---|
| `exceljs` | 워크북 정의 하나로 **CSV**와 **xlsx**를 모두 쓰고 읽는다 |
| `@Global()` `SpreadsheetService` | 모듈을 다시 import하지 않고 발주·실사가 공유한다. 언어에 대해서는 전혀 모른다 |
| `StreamableFile` | 생성한 파일을 다운로드로 스트리밍하면서 Nest의 응답 처리 안에 머문다 |
| `@Query()` + `ExportQueryDto` (`@IsIn`) | `?format=csv\|xlsx`, `?lang=en\|ko`를 검증하고, 아니면 400을 반환한다 |
| `FileInterceptor` + `ParseFilePipe` + `MaxFileSizeValidator` | 업로드된 시트를 받고 10MB로 제한한다 |
| `@HttpCode(200)` | 수정 가져오기는 수정하는 `POST`라서, 기본값 201 대신 200을 반환한다 |
| `BadRequestException({ message, errors })` | 객체를 넘기면 *그 객체*가 400 응답 본문이 되어 행별 오류 목록을 담는다 |
| `Readable.from(buffer)` (`node:stream`) | exceljs의 CSV 리더는 버퍼가 아니라 스트림을 받는다 |
| Prisma `{ in: [...] }` 묶음 조회 | 행마다 쿼리하지 않고 모든 바코드를 쿼리 두 번으로 찾는다 |

## 마무리

이번 슬라이스로 MinIO에서 시작한 파일 트랙이 끝났다. 이제 Inventra는 비공개 이미지를 저장할 **뿐 아니라**, 발주와 실사를 스프레드시트로 내보내고 가져온다. 두 형식, 두 언어를 지원하고, 가져오기는 모든 행을 저장하거나 하나도 저장하지 않는다. 마지막 상태는 **단위 테스트 210개, e2e 테스트 86개 통과**다.

가장 큰 교훈은 exceljs에 관한 게 아니었다. 구체적인 질문 하나를 던진 순간 요구사항의 모양이 바뀌었다는 점이다. "발주 파일"은 저장 기능처럼 들렸지만, 알고 보니 데이터 포맷이었다. 그다음부터 설계는 하나의 원칙을 따랐다. **컬럼 순서를 한 번 정하고, 나머지는 모두 거기서 읽게 한다.**

**다음:** 정해진 건 없다. 도메인은 완성됐고, 남은 일은 실제 필요에서 나온다. 안정적인 클라이언트와 어댑터가 나오면 Prisma 8로 마이그레이션하고, 캐싱이나 모니터링은 측정해서 이유가 확인된 뒤에만 한다.
